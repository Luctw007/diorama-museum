## 一、总则与定位

### 1.0 背景：为什么是现在

项目走到今天，内容包已经做到 15 台，规范迭代到 v0.5，校验器从 validate 一路长到 model_check、
audio_check、slot_check。但这些都是"横向做精"——把单台设备的契约打磨到极致。当设备规模的目标
从"几十台"跳到"数千上万台"，光靠横向做精就不够了，必须"纵向立骨架"：先有一套分类学，让上万
台设备各归其位；再有一套目录 schema，让上万条记录能被摄取、被索引、被检索。

这就是本专章"为什么是现在"的原因：它不是锦上添花的新功能，而是规模跃迁前必须补的地基。没有
分类学，上万台设备就是上万份散文档，谁也不知道"计算机大类下到底收了多少台个人机"；没有目录
schema，普查出来的一万行数据就是一万行格式各异的自由文本，系统吞不下、查不动。地基先立住，
后续的普查、摄取、索引、检索才有附着点。

### 1.1 目标

一座电子计算机博物馆，设备数量会从现在的几十上百，长到数千、甚至上万。到了万级规模，"机器
在哪、叫什么、属于哪类、什么年代、为什么值得收"这些信息如果还散落在各条线的文档里，系统就
无法摄取、无法索引、无法给参观者一个"按分类浏览、按关键词检索"的体验。

本专章要解决的就是这个"规模问题"的前置：**先立法分类学，再立法条目 schema**，让普查出来的
目录变成机器可读、可摄取、可索引、可人类阅读的统一数据资产。三个具体目标：

1. **一套三级 taxonomy**：大分类→中分类→子分类，覆盖计算机、游戏机、通讯、家电、外设、嵌入式
   全谱系，任何一台设备都能落到唯一路径；
2. **一个唯一 schema**：目录条目的字段、枚举、约束一次性定义清楚，03/05 线照此普查，01 线照此
   摄取，02 线照此校验；
3. **一套索引策略**：万级数据按中分类分片、枚举与自由文本分离、别名归一，保证摄取与查询都是
   毫秒级。

### 1.2 设计原则

1. **分类学先行，数据后行**：先定死"每台设备属于哪条路径"，再谈"这条路径下收了多少台"；
2. **枚举收紧，自由文本放开**：分类路径是枚举（只能落在 taxonomy 树内），名称/别名/影响力理由是
   自由文本（可自然增长）；二者分离，校验只管枚举、检索可走全文；
3. **唯一 id 全局判重**：每条目录一个全库唯一 id，格式自描述（大类码 + 中分类码 + 序号），
   让"重名不同机、同名不同 id"都能被机器判定；
4. **轻量优先，重查可选**：目录条目先做"轻量七列"（名称/年代/影响力/分类/状态），深度调研
   另行展开，不把万级数据压成百万级文档。

### 1.3 与 v0.5 槽位契约的衔接

v0.5 槽位契约的 `device_class` 枚举（computer/console/handheld/phone/pda/dedicated_av/other）
与本专章二级 taxonomy 的**大分类**同源。本专章把它扩展为三级（大→中→子），但保持大分类与
`device_class` 语义一致，避免"目录说它是计算机、槽位说它是游戏机"的冲突。

### 1.4 设计决策记录（裁决与理由）

**D1：目录是独立数据资产，不塞进内容包**。目录条目与内容包是"目录册"与"展品"的关系——目录册
记载"全库有哪些设备、什么年代、什么影响力"，内容包才是"某一台设备的完整数字化"。把目录塞进
内容包会让"还没做包但值得收的几千台设备"无处安放；独立出来后，目录可以先于内容包大规模生产，
系统也能先建起"全库导航"。

**D2：id 用"大类码+中分类码+序号"自描述格式**。相比纯自增数字，自描述 id 让"看一眼就知道它属于
哪个大分类哪个中分类"，也为分片存储提供了天然前缀。序号 6 位（可到 999999）为每个中分类留足
空间，万级规模绰绰有余。

**D3：分类路径用中文，id 用字母码**。人读的中文路径（`["计算机","个人机","PC 兼容"]`）与机读的
字母码（`C-PC-`）分离——普查员写中文不会拼错码，系统用码建索引不会因中文别称漂移。二者通过
id 前缀绑定，不需额外映射表。

**D4：影响力理由 ≤60 字**。60 字是"一句话说清为什么值得收"的硬上限，逼普查员提炼而非堆砌，也
天然规避了"复制大段百科简介"的版权风险。论据溯源交给 `sources[]`，不在目录里堆全文。

**D5：先轻量、后深度**。目录条目是轻量七列（名称/年代/影响力/分类/状态 + 厂商/产地），深度调研
（拆解、运行原理、技术参数）另行展开。这样万级普查是"填表"而非"写论文"，速度才撑得起规模。

## 一·五、典型场景演练

### 场景一：普查一台新设备（03 线计算机大类）

普查员发现一台 IBM PC 5150 值得收。他按本规范填一条目录：id 取 `C-PC-000123`（计算机大类的
个人机中分类，第 123 号），name 写规范名 "IBM Personal Computer 5150"，aliases 补 "IBM PC /
IBM 5150"，path 落 `["计算机","个人机","PC 兼容"]`，reason 写 "奠定 IBM PC 兼容机标准，开启
个人电脑时代"（19 字，≤60），status 因已产包写 `done` 并关联 `device_id: "ibm5150"`，sources
挂 `S53A-001` 指向普查台账里的资料来源。这条目录过 catalog_check（52-B）时：id 唯一、path 落在
taxonomy 树内、status=done 且带 device_id、reason 非空 ≤60 字——全部通过，进入摄取。

### 场景二：参观者按分类浏览全库

系统摄取全部目录后，按 §四策略分片建索引。参观者点"游戏机"→"家用机"，系统只读 `G__HC.jsonl`
一片（≤5k 条），按年代或名称排序呈现；再点某台 FC，看到它的名称、别名、年代、影响力一句话与
关联的内容包链接。整个过程毫秒级，因为查询只命中一个分片，而非全库扫描。

### 场景三：发现分类学遗漏

普查到一半，普查员发现"电子词典"这类设备在 taxonomy 里没有合适落点。按 §二，它暂时归入
"其他/未分类"，并在普查报告的"覆盖面自查表"里记一条"电子词典待 taxonomy 修正"。02 线在下一版
taxonomy 里吸收这类反馈，给"办公与计算外设"或"通讯与移动"增加相应子分类。分类学是活的，靠
普查反馈迭代，而不是一次定死。

### 2.3 分类路径格式

分类路径 `path` 为三级数组：`["大分类", "中分类", "子分类"]`，如
`["计算机", "个人机", "PC 兼容"]`。目录条目用中文路径（人读），系统索引同时保存大类码+中分类码
（机读）。分类路径必须**整条落在 taxonomy 树内**（CC-03 校验），不允许自由发明新层级。

### 2.4 分类学设计考量（为何这样切）

这套三级 taxonomy 的切法，遵循三条朴素的直觉：

**按"算力与用途"切大分类**。计算机（通用计算）、游戏机（娱乐计算）、通讯移动（随身计算）、
家电影音（消费电子）、办公外设（计算周边）、嵌入式工业（专用计算）、其他（兜底）——七大类
几乎互斥，任何一台设备都能凭"它是拿来干嘛的"落到唯一大类，不会出现"既是计算机又是家电"
的纠结。

**按"技术谱系"切中分类**。计算机大类下按历史谱系切（早期→大型机→小型机→个人机→工作站→
服务器→手持→超算），游戏机按形态切（家用/掌机/街机/游戏电脑）。谱系切法的好处是"同代、同
流派"的设备自然聚在一起，参观者按中分类浏览，就是在按技术史走一遍。

**按"关键差异"切子分类**。个人机的子分类（8 位家用/16 位/PC 兼容/日本国产）切的是"真正影响
使用与收藏的关键差异"——8 位家用机与 PC 兼容机在软硬件生态上判若两个世界，必须分开。子分类
不求穷尽，只求"把真正不同的分开，把大同小异的合并"。

这套切法不是学术分类学的照搬，而是"面向博物馆策展与检索"的工程分类——它优先保证"每台设备
有唯一落点"与"同谱系相邻"，牺牲了学术分类的部分严谨性，换取普查的可操作与检索的高效。学术
上的争议（如"工作站算不算个人机"）通过中分类并行并存解决，不强行归并。

简言之，这棵树的价值不在"分类得有多学术"，而在"每个人都能把一台设备放对地方、系统能顺着树
一秒找到它"。它是整章的地基，后面的 schema、索引策略都建立在"设备能唯一落点"这个前提上。

## 三、目录条目 schema 逐字段定义

### 3.1 顶层 schema（全量示例）

```json
{
  "id": "C-PC-000123",
  "name": "IBM Personal Computer 5150",
  "aliases": ["IBM PC", "IBM 5150", "PC 5150"],
  "maker": "IBM",
  "origin": "美国",
  "year": 1981,
  "path": ["计算机", "个人机", "PC 兼容"],
  "reason": "奠定 IBM PC 兼容机标准，开启个人电脑时代",
  "status": "done",
  "device_id": "ibm5150",
  "sources": ["S53A-001", "S05-014"]
}
```

### 3.2 字段总表（逐字段）

| 字段 | 类型 | 必需 | 说明 | 校验 |
|---|---|---|---|---|
| `id` | string | 是 | 全库唯一 id（大类码+中分类码+6 位序号） | CC-02 |
| `name` | string | 是 | 规范名称（主名） | CC-01 |
| `aliases` | array[string] | 否 | 别名数组 | CC-07 |
| `maker` | string | 否 | 厂商 | — |
| `origin` | string | 否 | 产地（国别/地区） | — |
| `year` | int | 否 | 年代（发布/上市年份） | CC-05 |
| `path` | array[string] | 是 | 分类路径 [大,中,子]，三级 | CC-03 |
| `reason` | string | 是 | 影响力理由（≤60 字，非空） | CC-06 |
| `status` | string(enum) | 是 | 状态 | CC-04 |
| `device_id` | string | 条件 | 关联包 device_id（done/package 必填） | CC-04 |
| `sources` | array[string] | 否 | 来源编号[]（支撑"影响力"论据） | — |

### 3.3 id 格式

`<大类码>-<中分类码>-<6位序号>`，如 `C-PC-000123`、`G-HC-000456`。

- 大类码：C/G/M/A/O/E/X（单字母）。
- 中分类码：2 字符（见 §2.2 各表），如 PC（个人机）、HC（家用机/手持计算，视大分类而定）。
- 序号：6 位十进制，从 000001 起，按中分类内连续递增。
- 正则：`^[CGM AOEX]-[A-Z]{2}-\d{6}$`（大类码字母集 + 中分类码 2 大写字母 + 6 位数字）。

> 注意中分类码在不同大分类下可复用（如 `HC` 在计算机=手持计算、游戏机=家用机），id 的全局唯一
> 靠"大类码"前缀保证，不会因中分类码复用而冲突。

### 3.4 status 枚举

| 值 | 含义 | device_id 要求 |
|---|---|---|
| `planned` | 计划收录（未开始） | 可空 |
| `researching` | 调研中 | 可空 |
| `package` | 内容包生产中 | **必填**（已开工但未完成） |
| `wip` | 包已完成待验收 | 可空（有包可关联，不强制） |
| `done` | 已完工作为展项 | **必填** |

> 与 01 线门禁 WIP 判据的呼应：`package` = 生产中的包（对应 `.wip` 标记语义），`wip` = 包已产
> 待验收。二者均指"内容包侧"状态，目录侧只记录阶段，不重复维护包的细节。

### 3.5 reason（影响力理由）

- 非空，且 ≤60 字（CC-06）。
- 只写"为什么这台设备值得收录"的一句话，不复制厂商/百科的受版权保护简介。
- 论据靠 `sources[]` 来源编号支撑（每台设备至少 1 个来源编号，来源明细在普查侧台账另记）。

### 3.6 sources（来源编号）

- 数组，元素为来源编号字符串，如 `S53A-001`（任务编号+序号）。
- 用途：支撑 reason 的论据溯源，避免"影响力理由"凭空断言；也方便后续把目录升级为"带引用的
  百科条目"。

### 3.7 逐字段"为什么存在"（字段设计意图）

每个字段都不是拍脑袋加的，背后各有一个要解决的现实问题：

- **name 与 aliases 分离**：一台设备往往有官方名、俗称、型号、缩写多种叫法（IBM PC 5150 就有
  "IBM PC""IBM 5150""PC 5150"），把主名与别名分开，检索才既准确（主名）又宽容（别名）；
- **maker 与 origin 分开**：厂商（谁造的）与产地（哪里造的）是两回事，IBM 是美国厂商但在全球
  多地生产，拆开才不误导；
- **year 单列且可选**：年代是目录最有用的排序维度之一，但很多早期设备年代考据困难，故设为
  可选 + 范围校验，宁缺毋滥；
- **path 三级固定**：三级足以表达"大/中/子"的粒度，再深一层（子→孙）会让普查员无所适从，
  浅一层（只有大/中）又不够区分"8 位家用"与"PC 兼容"这类关键差异；
- **reason 独立于 name**：name 回答"这是什么"，reason 回答"为什么值得收"，前者客观后者判断，
  分开才能既做索引又做策展；
- **status + device_id 联动**：目录要能回答"这台设备的包做到哪一步了"，done/package 必须带
  device_id 才能把目录与内容包钉在一起；
- **sources 数组**：让"影响力"可溯源，也把"需核实"的不确定性显式标出来，是普查质量的红线护栏。

## 七·五、普查质量红线与自查清单

普查规模大、人员多，质量不能只靠事后校验，还要靠事前红线和事后自查兜底：

**四条红线**：
1. **不编造**：厂商、年代、产地拿不准就留空 + 标「需核实」，绝不写查无实据的数据；
2. **不复制**：name/reason 只写自拟客观表述，不粘贴受版权保护的厂商/百科简介；
3. **不孤证**：每台设备的 reason 至少 1 个来源编号支撑，杜绝"影响力"凭空断言；
4. **不跳类**：path 三级必须落在 taxonomy 树内，拿不准归"其他/未分类"，不自由发明新层级。

**自查清单**（每批普查提交前逐项勾选）：
- [ ] 每条 id 唯一且格式合法（`大类码-中分类码-6位序号`）；
- [ ] 每条 path 三级齐全且落在 taxonomy 树内；
- [ ] 已产包的 15 台标 done 且带正确 device_id；
- [ ] 每条 reason 非空且 ≤60 字，且有 sources 支撑；
- [ ] 年代字段要么留空要么落在 [1880, 当年+1]；
- [ ] JSONL 与 Markdown 双份同步，条数一致；
- [ ] 过 catalog_check（52-B）零 FAIL。

## 四、万级索引策略

### 4.1 按中分类分片（每片 ≤5k）

- 摄取时按"大分类__中分类"切分片，每片最多 5000 条（01 线 catalog_ingest 已实现 `SHARD_MAX=5000`）。
- 分片文件命名 `C__PC.jsonl`、`G__HC.jsonl` 等；配 `manifest.json` 记录每片路径与条数。
- 好处：万级数据惰性加载——用户点开"个人机"才读 `C__PC` 一片，而不是一次性把全库读进内存。

### 4.2 枚举与自由文本分离

- **枚举字段**（机器可校验、可建精确索引）：`path`（分类路径）、`status`、`id` 前缀。
- **自由文本字段**（全文检索、模糊匹配）：`name`、`aliases`、`maker`、`reason`。
- 二者用不同索引：枚举走字典树/哈希，自由文本走归一化后的倒排索引。

### 4.3 别名归一规则

- 归一化（01 线 `_norm` 已实现）：去除所有空白字符 + 统一小写。
- 例："IBM PC" 与 "ibm pc" 与 "IBM_PC" 归一后同键，检索"ibm pc"能命中三者。
- 别名去重：同一设备的 aliases 内去重；跨设备同名不同 id 由 id 唯一性兜底（不判重名错，只告警）。

### 4.4 为什么分片策略能撑住万级

万级数据的最大敌人不是"存不下"，而是"读不动"——如果每次打开目录都要把一万条全读进内存、全
扫一遍，前端就会卡。分片策略的解法是"按需加载"：把一万条按 31 个中分类切成 31 片（每片最多
几百到几千条），用户点开哪个中分类，系统只读那一片。这样单次查询的代价从 O(全库) 降到
O(单中分类)，万级与千级在体验上几乎无差别。

枚举与自由文本分离，则是让"精确"与"模糊"各走各的路：分类路径是枚举，用户点"个人机"是精确
导航，走哈希索引瞬间命中；用户输"apple"是模糊检索，走名称/别名的归一化倒排，返回所有含
"apple"的条目。两套索引互不干扰，也不会因为自由文本的噪声拖慢枚举导航。

这套策略已经在 01 线 catalog_ingest 与 scale_bench（51-A）里落成了可运行代码与性能基准——本
规范是它的"数据契约上游"，二者配合，万级目标从"口号"变成"有基准可查的工程结论"。

### 5.1 映射表的使用约定

这张映射表解决的是"新老两套分类并存"的过渡期问题：内容包在 v0.2 就定义了 `meta.category`
（early-computer/mainframe/minicomputer/personal-computer/game-console/console 等旧枚举），而目录
要用新的三级 taxonomy。两者不能互相打架，也不能一刀切把旧的废掉（会破坏存量包）。

过渡期的约定是**新目录以 path 为权威、旧 meta.category 仅作轻量提示**：目录条目一律写三级 path，
内容包的 `meta.category` 保留不动（它是内容包的轻量门类，供门禁/索引快速归类），需要桥接时查
本表即可。这样存量 15 包不用改，新目录又能用新分类学，代价只是多一张映射表。

映射表本身也暴露了一个事实：旧 `meta.category` 的粒度比新 taxonomy 粗——`personal-computer`
一个值，对应新 taxonomy 里"个人机"中分类下的多个子分类（8 位家用/16 位/PC 兼容/日本国产）。
所以映射方向是"旧→新的中分类"，再由普查时的人工判断落到具体子分类，映射表无法、也不该替人
做这个子分类判断。

## 六、输出格式契约

### 6.1 机器可读 JSON Lines

- 每行一个 JSON 对象（一个目录条目），UTF-8 无 BOM，行尾 `\n`。
- 文件名：`<大分类>大类_目录_v<版本>.jsonl`，如 `计算机大类_目录_v1.jsonl`。

### 6.2 人类可读 Markdown

- 按大分类→中分类分组，每组一张表，列：id / 名称 / 别名 / 厂商 / 年代 / 子分类 / 状态 / 影响力一句。
- 每张表前加中分类名 + 条数；文末附覆盖面自查表（哪些中分类未覆盖）。

### 6.3 双份生成规则

- JSONL 是**权威**（机器摄取、校验的对象）；Markdown 是**渲染视图**（供人读）。
- 二者同源：Markdown 由 JSONL 渲染生成（或反之，普查侧保证同步），不允许手改 Markdown 而 JSONL 不同步。

### 6.4 双份为什么缺一不可

机器与人是两种完全不同的"读者"，单靠一份满足不了双方。机器要的是稳定、无歧义、可逐行解析的
JSONL——每个字段有类型、每行一条记录、坏一行只影响一行；人要看的是分好组、排好序、有表头的
Markdown——一眼看清"计算机大类下有多少中分类、每个中分类收了多少台"。JSONL 给人看是灾难
（一堆花括号），Markdown 给机器读是灾难（表格难解析）。所以定"双份同源"：JSONL 是权威数据源，
Markdown 是从它渲染出来的视图，二者永远同步，谁也不许脱离对方单飞。

## 结语

分类学与目录专章要回答的问题，是项目在"数千→上万"规模跃迁前必须先想清楚的三个问题：**设备
怎么分类、每条目录长什么样、万级数据怎么又快又稳地存取**。本章给出的答案是——一套 7 大分类、
31 中分类、约 90 子分类的三级 taxonomy；一个 11 字段、含枚举与约束的目录条目 schema；一套按
中分类分片、枚举与自由文本分离、别名归一的索引策略。

它把"普查—摄取—索引—检索"这条链路的数据契约一次立住，让 03/05 线知道"怎么填"、01 线知道
"怎么读"、02 线知道"怎么判"（52-B catalog_check）。分类学不是一次定死的，它靠普查反馈迭代；
但 schema 与索引策略必须先行定稿，否则万级数据就是一堆无法摄取、无法索引的散文档。这正是
"分类学先行"的全部意义。

后续推进路径：52-B 落地 catalog_check 校验器；03/05 线按本章 schema 与模板产出首批目录并过
校验；01 线 catalog_ingest 摄取建索引；普查中暴露的分类学遗漏回填到下一版 taxonomy。待这些
闭环后，本草案升版为 v0.6 正式章并入《内容包规范》正文。

## 七、给 03/05 线的普查模板

### 7.1 首行示例（JSONL 单行）

```json
{"id":"C-PC-000123","name":"IBM Personal Computer 5150","aliases":["IBM PC","IBM 5150"],"maker":"IBM","origin":"美国","year":1981,"path":["计算机","个人机","PC 兼容"],"reason":"奠定 IBM PC 兼容机标准，开启个人电脑时代","status":"done","device_id":"ibm5150","sources":["S53A-001"]}
```

### 7.2 批量生产注意事项

1. **不复制受版权简介**：`name`/`reason` 只写自拟的客观一句，禁止粘贴厂商/维基百科的受版权段落；
2. **reason 必须由 sources 支撑**：每条 reason 至少 1 个来源编号，来源明细另建台账（不在目录里堆全文）；
3. **拿不准标「需核实」**：厂商/年代/产地不确定的，在对应字段留空并在 sources 里标"需核实"，
   不编造数据（红线）；
4. **已产包的 15 台标 `done`**：必须带 `device_id`，与内容包一一对应；
5. **分类路径用本表枚举**：`path` 三级必须落在 §2.2 taxonomy 树内，拿不准归"其他/未分类"；
6. **id 连续不重号**：按中分类内序号递增，普查完跑 catalog_check 判重。

### 7.3 普查产出物结构与验收口径

每批普查提交一个目录，结构如下（以 03 线计算机大类为例）：

```
03/repo/docs/catalog/
  计算机大类_目录_v1.jsonl    # 权威数据（每行一条，过 catalog_check）
  计算机大类_目录_v1.md       # 人类可读视图（分中分类表格）
  TASK-53A_完成报告.md        # 统计表 + 覆盖面自查 + 与 taxonomy 出入清单
```

验收口径（对口 52-B）：
- `catalog_check` 零 FAIL（缺字段/重 id/路径不存在/状态缺 device_id/年代越界/理由超长全部通过）；
- 条数达到普查任务的覆盖要求（如 53-A 的 ≥300 条）；
- 覆盖面自查表如实列出"哪些中分类没覆盖到"（列入 next 批，而不是假装覆盖）；
- 与 taxonomy 的出入清单（哪些设备找不到落点、归了"其他/未分类"）回传给 02 线做 taxonomy 迭代。

这套"普查产出物 + 验收口径"让 03/05 线的批量生产有章可循：先照模板填、再照清单自查、最后过
校验器，环环相扣，质量在入口就被兜住，而不是等万级数据堆成山再去翻修。规模越大，入口兜底
越值钱——一条坏数据在入口拦下是零成本，混进一万条里再找出来就是大海捞针。

## 附录 B·五、FAQ（高频疑问与边界澄清）

**Q1：目录与内容包到底什么关系？会不会重复？**
不重复。目录是全库的"导航册"，一条目录 = 一台设备的轻量登记（名称/年代/影响力/分类/状态）；
内容包是某一台设备的"完整数字化"（模型/标注/运行时）。一台设备可以"已进目录但还没做包"
（status=planned/researching），也可以"既有目录又有包"（status=done 且带 device_id）。目录先行、
内容包跟进，是支撑"数千→上万"规模的关键。

**Q2：为什么 id 不用简单的自增数字，而要用 C-PC-000123 这种带码的？**
因为自描述 id 同时是"全局唯一键"与"分片前缀"。看到 `C-PC-` 就知道它属于计算机大类的个人机
中分类，系统据此把它写进 `C__PC.jsonl` 分片；查询"个人机"时只读这一个分片。纯数字 id 无法
从键本身读出归属，还得另查映射表，多一跳就多一分复杂度。

**Q3：分类路径 path 是中文，机器怎么建索引？**
path 是枚举——它只能落在 taxonomy 树内（catalog_check 的 CC-03 校验这一点）。系统在建索引时，
把中文 path 映射到 id 前缀的字母码（C-PC 等）做精确索引；中文 path 保留给人读。枚举字段走精确
哈希，自由文本（名称/别名）走归一化倒排，两套索引各司其职。

**Q4：同一台设备有不同的名字（别名）怎么办？会不会被当成两台？**
靠 `aliases[]` 归一。IBM PC、IBM 5150、PC 5150 都是同一台（id=C-PC-000123），放进它的 aliases。
检索时归一化（去空白+小写）让"ibm pc"能命中它们。跨设备同名不同 id 的情况由 id 唯一性兜底
（只告警不判错），因为现实里确实存在两台不同设备叫同一个名字。

**Q5：影响力理由（reason）为什么要限 60 字？**
一是防复制——60 字逼你写自己的判断，而不是粘贴受版权保护的百科简介；二是防注水——60 字足够
说清"为什么值得收"，堆到 300 字反而稀释了信息。论据溯源交给 sources[]，目录里只留结论。

**Q6：年代字段 year 填不准怎么办？**
填发布/上市年份即可，拿不准就留空（year 是可选的，但一旦填了就要落在 [1880, 当年+1] 范围内，
catalog_check 的 CC-05 校验）。编造年代是红线——宁可空着，也不要写一个查无实据的年份。

**Q7：这套 schema 能撑到一万条吗？**
能。分片（每中分类 ≤5k）+ 枚举与自由文本分离 + 别名归一，保证摄取是 O(n) 一次性建索引、
查询是 O(1) 命中分片。01 线 scale_bench（51-A）已实测万级合成数据的摄取代价与查询性能，证明
"万级可行"；本规范的 schema 与索引策略正是让这个性能可持续的数据基础。
