## 章 〇：总则与设计目标

### 〇.1 为什么 1.0 要"规范先行"

v0.1 阶段的教训是：内容线和引擎线并行推进时，凡没有规范先行的字段（如 media_class、槽位
manifest 的 media_classes 枚举、目录键名），都会在事后发生跨线分叉，再返工对齐。1.0 的体量更大
——约 55~75 子任务、6~8 轮，新增品类、多设备堆叠大厅、四厅台本、真跑矩阵扩展这四类量产，
每一类都同时牵动 03（内容）、04（体验）、05（游戏机/家电）、01（引擎/槽位）四线。如果不先把
"字段长什么样、枚举值有哪些、存量怎么兼容"写清楚，内容线就只能"各写各的"，最后在门禁前爆发
大规模返工。本草案的价值不在于"现在就能照此实现"，而在于"给量产一个可对齐的参考口径"，让
后续正式定稿时无需推倒重来。

### 〇.2 与现行规范体系的关系

- 本草案**不是** v0.6 的替代，而是 v0.6 之后、1.0 量产之前的**前瞻规划章**；定稿后以"增补章"
  并入《内容包与目录规范》，不升主版本（沿用 v0.6.x 增补惯例）。
- 本草案**不落编号**：条文用 `v0.7-` 章序（章 A~E）标识，不占用 CC / REF / GN / R 任何编号空间；
  定稿时若确需新校验规则，按《编号与路径_封版收口_v1》的空缺号裁决另行立项续编，本草案一律不预占。
- 本草案**不改任何工具**：taxonomy.json、schema、emulators_registry.json、catalog_check、media_infer
  均保持现状，草案里的字段/枚举提案只以文字呈现。

### 〇.3 五章之间的关系

章 A（media_class 扩展）是"目录侧"的品类基础，章 B（堆叠布局）与章 C（导览台本）是"展陈侧"的
体验基础，章 D（真跑矩阵）是"运行侧"的深度基础，章 E（兼容条款）是贯穿四者的红线。四条线对应
四类量产，缺一不可，但落地优先级不同：章 A 与章 E 最优先（新品类一开题就用），章 B/C/D 可随
对应线量产节奏逐章定稿。

## 章 A：media_class 新品类扩展（草案）

> 草案状态：**草案**（枚举收口为「待 01 线确认」，品类覆盖提案为「依赖 03/04/05 线」）。
> 基线依据：`规范增补_v0.6.1` §一 media_class 推定规则章、附录开放问题 1/2/3。

### A.1 收口 v0.6.1 附录开放问题 2：「无」是否入枚举

- **现状**：v0.6.1 §1.1 的 media_class 枚举为八大类目（`cartridge / disk / tape / cd / dvd / card /
  firmware / app_package`）外加补充值「无」（无介质设备，如电视/打印机/输入设备）。「无」目前只是
  media_infer 的输出占位，**未正式入枚举**。
- **本草案建议**：正式新增枚举值 **`none`**，取代中文占位「无」。理由：①「无」作为中文值无法与
  `runtime.slot.media_class` 的英文枚举对齐，机器判定要用稳定英文键；② 1.0 新增的大规模外设/家电
  品类（电视、显示器、打印机、扫描仪、输入设备）大量属于"无介质"设备，必须有一个正式枚举落点。
- **待确认点**：`none` 入枚举是「只增不改」的新增，不影响既有八类，但需要 01 线槽位加载器
  `media_classes` 白名单与 02 线 `media_infer.py` 同步纳入，故标「待 01 线确认」。

### A.2 1.0 新品类/新设备的 media_class 覆盖提案

1.0 全馆新增品类将突破现有"计算机/游戏机/通讯/家电"框架，media_class 需按下表覆盖（每项都是
**提案**，最终取值须以设备真实介质为准，凡不确定处标「需核实」，不得杜撰某设备"确有某介质"）：

| 新品类/新设备 | 现有枚举能否覆盖 | 本草案提案 |
|---|---|---|
| 机械设备（后期加入） | 不能（无电子介质） | 建议归 `none`，另议是否新增 `mechanical` 子类（暂缓） |
| 掌上电子宠物（Tamagotchi 等） | 不能（内置固件、无外插介质） | 归 `firmware`（内置固件） |
| GSM→智能手机演进（大哥大→GSM→智能手机） | 部分（`firmware` / `app_package`） | 大哥大/GSM 归 `firmware`；智能手机归 `app_package`（应用包） |
| VCD/DVD 播放机 | 能（`cd` / `dvd`） | 沿用 `cd` / `dvd`，无需新增 |
| 大规模销售硬件（收录机/复读机/计算器等） | 部分（`tape` / `none`） | 收录机归 `tape`；计算器归 `none` |

### A.3 枚举治理原则

- **九枚举只增不改、向后兼容存量回填**：八大类目 + 拟新增 `none` = 九枚举，一经定稿只允许**新增**
  值，不得改名、不得删除既有值；存量目录的 `media_class` 回填不因新增值而作废。
- **回填触发**：1.0 新品类目录条目按 §A.2 提案回填 `media_class`，回填走"推定建议 → 人工复核 →
  写回目录"既有链路（`media_infer.py` → 回填工作表 → 03/05 线确认），不新增旁路。

## 章 B：多设备堆叠展厅布局（草案）

> 草案状态：**草案**（字段为「reference 型声明」，**待 01 线确认**是否 1.0 内实现；
> 内容语义「依赖 03/04/05 线」）。
> 背景：1.0 四厅（黎明厅/大型机小型机/个人机厅/游戏机与家电厅）将多台设备同屏展陈，需要一套
> "展厅布局"声明字段，让内容包能描述"我摆在哪、和谁叠在一起、同屏最多激活几台"。

### B.1 展厅布局字段草案（reference 型声明）

以下字段为**声明式草案**，只描述"应该有什么"，**不要求 01 线马上实现**；字段名与类型均为提案：

| 字段 | 类型 | 说明 |
|---|---|---|
| `hall` | string | 所属展厅标识（如 `dawn` / `mainframe` / `personal` / `console`） |
| `exhibit` | string | 展位标识（展厅内唯一，如 `dawn-01`） |
| `stack` | array | 堆叠分组（同组设备在物理上叠放/相邻，如机柜组/工作台组） |
| `position` | array[3] | 展位坐标（相对展厅原点，提案 +Y 上，与 Godot 一致） |
| `co_active_max` | int | 同屏同时激活上限（建议默认 3，超限降级为静态展示） |
| `lod_level` | string | 默认 LOD 档（对齐 v0.3 建模章三档：特写/观察/远景） |
| `media_concurrency` | int | 媒体并发上限（音频/视频同时发声台数，防混音溢出） |

### B.2 与 v0.3 建模章的衔接

- 堆叠布局的 `lod_level` 与 v0.3 建模网格章的三档 LOD 预算表（特写 50k / 观察 20k / 远景 8k）同源：
  展厅远景多台同屏时，每台取 `远景` 档，保证同屏总量可控。
- `co_active_max` 与 `media_concurrency` 是 1.0 特有的性能/体验约束，v0.3 未覆盖，属本章新增提案。

### B.3 落地顺序建议（供 01 线参考，非强制）

先只落地 `hall` / `exhibit` 两个**静态定位**字段（内容包能声明归属即可），`stack` / `co_active_max` /
`media_concurrency` 等**动态调度**字段留到 1.0 中后期，随同屏调度器一起实现。这样内容量产不必等引擎。

## 章 C：导览台本 schema（草案）

> 草案状态：**草案**（「依赖 04 线」四厅台本；字段与 04 线 60 号用例、音频事件规格对齐后再定稿）。
> 背景：1.0 四厅要"能导览"，导览是"按顺序走到各站、触发解说、看标牌"的序列，需要一份台本 schema。

### C.1 tour 序列草案字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `tour_id` | string | 台本标识（如 `tour-dawn-v1`） |
| `title` | string | 台本标题 |
| `stops` | array | 站点序列（顺序即导览顺序） |
| `stops[].stop_id` | string | 站点标识（关联展位/设备） |
| `stops[].trigger` | string | 触发方式（进入展位 / 手动 / 自动轮播） |
| `stops[].voice_ref` | string | 解说音频引用（对齐 v0.4 音频章 `vo_厅_站_句编号`） |
| `stops[].sign_ref` | string | 标牌引用（关联标注/百科条目） |

### C.2 与 v0.4 音频章、04 线台本的衔接

- `voice_ref` 直接用 v0.4 音频章的 `vo_厅_站_句编号` 命名，台本不必重定义音频命名。
- 台本正文（解说词、转场词）由 04 线四厅台本提供，本章只定义**结构化序列字段**，不复制台本全文。
- 每个 `stop` 可缺省 `voice_ref`（纯标牌站）或 `sign_ref`（纯解说站），保证单站可独立成文。

### C.3 设计原理：台本只做"结构"，不做"全文"

台本最容易做成两份割裂的东西：一份是 04 线写的中文解说词（人读），一份是引擎要读的触发序列
（机读）。若把解说词原文塞进机读字段，改一句词就要动两份，极易漂移。本草案的取舍是：**台本
schema 只承载"结构"**（顺序、触发、引用），解说词/转场词正文仍归 04 线台本文件，`voice_ref` 与
`sign_ref` 用引用键把它们串起来。这样改词不改结构、改结构不动词，两侧各改各的、由引用键收口。

## 章 D：真跑矩阵与槽位扩展（草案）

> 草案状态：**草案**（「待 01 线确认」后端接入顺序；「依赖 03/05 线」提供真跑机种内容包）。
> 背景：v0.1 真跑矩阵是三台（MAME apple2 / SIMH pdp8 / Stella），1.0 要扩到 ≥5 台真跑。

### D.1 3 台 → ≥5 台真跑登记口径

- **登记母表**：真跑机种一律登记进 `emulators_registry.json`（单一真相源，`规范增补_v0.6.2` §一），
  `status=bone` 表示"成熟可接入"。
- **可扩展字段提案**（registry 侧，只增不改既有字段）：`gateway_key` / `slot_manifest` /
  `ci_involved` 已在 97-B 补入；1.0 建议再增 `run_priority`（接入优先级，int）与
  `verified_by`（真跑验证人/用例号），供"真跑矩阵"排序与验收追踪。
- **槽位 manifest 可扩展字段提案**：现有 `slot_id/device_class/backend_type/binary/media_classes` 等；
  1.0 建议增 `run_status`（`dry-run` 干跑 / `live` 真跑）标记，区分"门禁能过但用户尚未装二进制"与
  "真跑已验证"两种状态。

### D.2 新增机种的后端接入顺序（供 01 线参考，非强制）

1. 先看 `emulators_registry` 是否有 `bone` 条目（成熟后端可直接接）；
2. 无 `bone` 则看 `reserved`（预留待映射）→ 需补 `module` 与二进制；
3. 仍无则走「新增槽位 manifest + 专用后端归 `dedicated`」路径（v0.5 槽位契约）；
4. 每台接入后跑 `release_check.py` 复验 R2（三槽位三许可），1.0 阈值随真跑台数上调（≥5）。

## 章 E：向后兼容与追溯条款（草案，但方向硬性）

> 草案状态：**草案**（本条款方向为硬性约束，即使草案也不可违背；最终定稿必须沿用）。
> 本条是全章的红线，回指"规范变更不得全量否决存量"的长期原则。

### E.1 非强制声明

v0.7 全部条文为**草案、非强制**：03/04/05/01 线可以先行量产，但量产字段须以本章为参考口径，
避免与后续定稿冲突；定稿前本章不进入 `content/schema`、不进入任何校验器、不进入 verify_all 门禁。

### E.2 不得全量否决存量

任何条文最终定稿，**不得全量否决存量**：即不得导致存量 **31 台包**、**目录 1582 条**、
**门禁 37/37** 的既有 PASS 回退为 FAIL。新增约束只能以"新增字段 + 默认值"方式落地，存量包不填
新字段也不得报错。

### E.3 升级路径三态（逐条标注）

每条文定稿时，必须逐条标注升级路径：

| 路径 | 语义 | 适用 |
|---|---|---|
| `push` | 新增字段/值，存量不受影响（不填不报错） | 新品类 media_class、展厅布局字段 |
| `soft` | 默认值回流，存量不报错、新包建议填 | media_class 推定值、LOD 档位 |
| `deprecated` | 旧字段/值限存量保留，新包禁用 | 存量中文字段、legacy input_map 字符串 |

> 存量 31 台包只允许被 `push`（新增）或 `soft`（默认值回流）两种方式触碰；任何 `deprecated`
> 只针对"限存量"，不得反手要求存量包立即改造（改造排期另行立项）。
