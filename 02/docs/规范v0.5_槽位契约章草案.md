## 一、总则与定位

### 1.1 目标

本项目要"装下一座电子计算机博物馆"，横跨从曼彻斯特 Baby 到红白机、再到手机与 DVD 播放机的
几十上百台设备。如果每接一台新模拟器都要改网关代码、每放一份介质都要手写配置，那么内容线
（03/05）与引擎线（01）之间就会陷入无穷无尽的联调与等待。

槽位契约的目标，就是把这种"接设备"的成本压到最低，让接入动作退化成两件事：**放二进制 + 写
一份 manifest**。这正是 Batocera 一类怀旧游戏发行版的成熟体验——用户把 ROM 丢进约定目录、
模拟器自动出现在列表里。本规范要把它形式化，落到三个可执行目标：

1. **零代码接入**：新模拟器接入 = 放二进制 + 写 manifest，不改任何 Python/网关代码；
2. **介质即插即用**：介质放入约定目录，网关 / doctor / 门禁自动发现；
3. **契约即裁判**：manifest 与介质目录放错即刻报错（47-B slot_check 落地）。

### 1.2 适用对象

- `slots/emulators/<slot_id>/manifest.json`：模拟器槽位声明，是本规范的**核心客体**；
- `slots/media/<media_class>/<device_class>/<slot_id>/`：介质（ROM/固件/镜像）目录；
- 内容包 `runtime` 的 `slot` 提示字段（回填建议见第七章）。

### 1.3 命名与目录顶层约定

```
slots/
  emulators/<slot_id>/manifest.json     # 槽位声明（本规范定 schema）
  emulators/<slot_id>/<binary 文件>     # 模拟器二进制（可选；native 后端无需）
  media/<media_class>/<device_class>/<slot_id>/   # 介质目录（三层嵌套）
```

- `slot_id`：kebab-case，= 目录名 = 网关注册键；全仓库唯一。
- 红线（FR-E3）：**本仓库永不下载、永不随附真实二进制与介质**，只有接口、位置与样例。

### 1.4 设计原理（为何这样分层）

槽位系统把"模拟器"与"介质"拆成两棵树，分别用 `emulators/` 与 `media/` 承载：

- **模拟器按槽位**：`emulators/<slot_id>/` 一层到底——一个槽位 = 一个模拟器后端 + 一份 manifest，
  不按设备类目再套一层，因为同一后端常服务多个设备（MAME 可跑 apple2 也可跑别的），按后端平铺
  最省事；
- **介质按类目×设备×槽位三层**：介质天然有"类目"（卡带还是软盘）、有"设备"（哪台机器）与
  "槽位"（哪个后端来跑），三层嵌套让"某台机器用某后端跑某类介质"这一事实可以直接从路径读出，
  无需任何注册表。

这条分层逻辑贯穿本规范：**谁扁平、谁分层，由"复用关系"决定**——后端可复用所以平铺，介质
不跨设备复用所以分层。

### 1.5 与既有规范的关系

槽位契约不是凭空新增的孤岛，而是对 v0.2 到 v0.4 既有规范的一次"引擎侧补全"。内容包规范一路
迭代下来，管住了内容包内部的契约数据（meta/runtime/annotations）、建模网格、音频资产，但始终
没有回答一个问题：**模拟器二进制与介质这类"运行时外部资产"该以什么契约管理**。

- 与 v0.3 建模章的关系：建模章管"设备长什么样"（网格、材质、预算），槽位章管"设备怎么跑"
  （二进制、介质、后端），二者正交——一台设备可以既有精致模型，又有一个能真跑的槽位。
- 与 v0.4 音频章的关系：音频章管"设备怎么响"（sounds/audio 资产），槽位章管"设备怎么跑"
  （模拟器），二者同属"可玩"维度，但资产形态不同（音频是内容包内文件，二进制/介质是用户
  自备的外部文件）。
- 与 v0.2 运行时契约的关系：`runtime.emulator`、`runtime.media_hint`、`runtime.bios_required`
  这些字段在 v0.2 就已存在，但它们只是"提示"，没有配套的目录契约与校验器。槽位章把它们从
  "松散提示"升级为"可校验契约"——`slot` 字段 + slots/ 目录 + slot_check 三者闭环。

一句话：槽位章是内容包规范在"运行时外部资产"维度的收口，它让"可玩"从口号变成"放文件就能玩"。

### 1.6 术语先行（本节为后续章节的阅读锚点）

在进入逐字段定义前，先把本专章反复出现的几个核心术语钉死，避免后文歧义：

- **槽位（slot）**：一个模拟器后端的挂载点，由 `slots/emulators/<slot_id>/` 目录 + 一份
  manifest.json 构成；注册后即成为网关 EMULATORS 表的一个键。
- **槽位 id（slot_id）**：槽位的唯一标识，等于目录名、等于网关注册键，kebab-case。
- **manifest**：槽位的声明文件，写满"这个槽位是什么后端、吃什么介质、什么许可、能不能存档"。
- **介质（media）**：ROM、固件、磁盘/磁带/光盘镜像等用户自备的运行时数据，按三层目录组织。
- **后端（backend）**：真正执行模拟的程序（MAME/SIMH/Stella/Mesen 或自研专用后端），
  与网关以独立进程 + 协议通信隔离。
- **注册表（EMULATORS）**：网关内存里的"模拟器键 → 后端模块/二进制/许可"映射表，
  槽位装载器把 manifest 动态并入其中。
- **三件套**：许可分档（tier）+ 来源 URL + 获取日期，是权属合规的最小登记单元。

## 二、manifest.json schema 逐字段定义

### 2.1 顶层 schema（全量）

```json
{
  "slot_id": "mame-apple2",
  "device_class": "computer",
  "backend_type": "mame",
  "description": "MAME apple2 驱动（需用户提供 MAME 二进制）",
  "license": {
    "tier": "gpl-2.0-or-later",
    "url": "https://www.mamedev.org/legal.html",
    "date": "2026-11-04",
    "doc": "licenses/MAME.md",
    "note": "MAME 上游 GPLv2+/BSD-3-Clause 双许可，版本需核实"
  },
  "binary": "mame",
  "binary_env": "MAME_BIN",
  "media_classes": ["disk", "tape"],
  "capabilities": {"frame": true, "audio": true, "input": true, "save": true},
  "keymap": "keys/keymap_apple2.json"
}
```

### 2.2 字段总表（逐字段）

| 字段 | 类型 | 必需 | 说明 | 校验（SV） |
|---|---|---|---|---|
| `slot_id` | string | 是 | 槽位名 = 网关注册键 = 目录名，kebab-case | SV-02 |
| `device_class` | string(enum) | 是 | 设备类目（见 3.1） | SV-02 |
| `backend_type` | string(enum) | 是 | 后端类型（见 3.2） | SV-02 |
| `description` | string | 是 | 描述（doctor/门禁展示） | SV-02 |
| `license` | string \| object | 是 | 许可（三件套对象或简写字符串，见 2.9） | SV-04 |
| `binary` | string \| object | 否 | 二进制（相对路径，多架构允许表见 2.6） | SV-03 |
| `binary_env` | string | 否 | 环境变量覆盖名（优先于 binary 探测） | SV-02 |
| `media_classes` | array(enum) | 否 | 支持的介质类目（见 4.2） | SV-02 |
| `capabilities` | object | 否 | 四能力位（见 2.10） | SV-02 |
| `keymap` | string \| null | 否 | 键码表路径（缺省走三级回退） | SV-02 |

下面逐字段展开说明，每个字段都给出"是什么、为什么、怎么写、怎么写错会怎样"。

### 2.3 slot_id

- kebab-case（小写字母、数字、连字符），如 `mame-apple2`、`simh-pdp8`、`fake-slot`。
- 必须与所在目录名一致（`slots/emulators/<slot_id>/manifest.json` 中 slot_id == 目录名）。
- 与网关注册键一一对应：`slot_id` 冲突时**内置注册优先**（46-A 已实现"同名跳过"）。

为什么 slot_id 就是目录名？因为目录名是文件系统里唯一、稳定、无需额外解析的标识，把它复用作
网关注册键，就消除了"manifest 里的名字"与"目录里的名字"二义的可能。任何人在文件管理器里看到
`slots/emulators/mame-apple2/`，就能立刻知道网关里对应键是 `mame-apple2`。

### 2.4 device_class（设备类目枚举）

| 值 | 含义 | 示例设备 |
|---|---|---|
| `computer` | 通用计算机（个人电脑/小型机/大型机/早期计算机） | apple-ii、pdp8、eniac |
| `console` | 家用游戏机 | famicom、sega-md、atari-2600 |
| `handheld` | 掌机 | Game Boy（预留） |
| `phone` | 手机 | 早期手机（预留） |
| `pda` | 掌上电脑/PDA | Palm（预留） |
| `dedicated_av` | 专用视听家电（VCD/DVD 播放机等） | DVD 播放机（预留） |
| `other` | 其它/未知 | 兜底 |

与内容包 `meta.category` 的映射：`early-computer` / `minicomputer` / `mainframe` /
`personal-computer` → `computer`；`game-console` → `console`。映射表见第七章回填建议。

`device_class` 的作用是**路由介质目录的第二级**，也是 doctor 与前端做"按类目过滤展项"的抓手。
它刻意做了宽松设计（7 项，含 `other` 兜底），避免未来出现"某类设备没处放"的死角。

### 2.5 backend_type（后端类型枚举）

| 值 | 含义 | 对应模块 | 备注 |
|---|---|---|---|
| `native` | 仓库自带/原生（零外部二进制） | `gw.emulators.fake_emulator` | 样例与演示用 |
| `mame` | MAME 后端 | `gw.emulators.mame_apple2` | 需用户提供二进制 |
| `simh` | SIMH 后端 | （预留） | 小型机/大型机 |
| `stella` | Stella 后端 | （预留） | Atari 2600 |
| `mesen` | Mesen 后端 | （预留） | FC/NES |
| `mobile` | 移动端后端 | （预留） | 手机/掌机 |
| `dedicated` | 专用后端（自研/第三方非主流模拟器） | （预留） | VICE/BeebEm/PC-86 等 |

> **裁决**：47-A 任务枚举原为 `mame/simh/stella/mesen/mobile/dedicated`（6 项），
> 01 线 46-A 实现额外引入 `native`（fake-slot 零二进制样例）。本规范**吸收 `native`**（7 项），
> 理由：`native` 表达"仓库自带后端、无需外部二进制"这一真实语义，缺它无法声明 fake/demo 槽位。

`backend_type` 是 manifest 里最重要的字段——它决定槽位映射到哪个后端模块、进而决定"真跑还是
演示降级"。真实后端（mame/simh/stella/mesen）目前只有 mame 有模块，其余为预留位；`dedicated`
是给那些"既不是 MAME/SIMH 也不是 Stella/Mesen"的专用模拟器（VICE、BeebEm、BlastEm、PC-86）
预留的统一入口。

### 2.6 binary（相对路径 + 多架构允许表）

- **简写（string）**：`"binary": "mame"` —— 跨平台同名，loader 自动探测 `.exe` 变体
  （46-A `_binary_path` 已实现 `mame` / `mame.exe` 双候选）。
- **多架构表（object）**：键为架构，值为相对槽位目录的文件名：

```json
"binary": {
  "x86_64-windows": "mame.exe",
  "x86_64-linux": "mame",
  "aarch64-macos": "mame"
}
```

- **允许的架构键**（白名单）：`x86_64-windows` / `x86_64-linux` / `aarch64-linux` /
  `x86_64-macos` / `aarch64-macos` / `wasm32`。未知架构键 → SV-02 WARN。
- **缺省**（无 `binary` 字段）：表示后端无需外部二进制（native 类）。

为什么需要"多架构允许表"？因为同一模拟器在 Windows / Linux / macOS 上的可执行文件名不同
（`mame.exe` vs `mame`），而槽位目录要能被跨机复制。多架构表把"这台机器该取哪个文件"写进
manifest，loader 按宿主平台自取，避免了"换个系统就找不到二进制"的尴尬。

### 2.7 binary_env

- 环境变量名，优先于 `binary` 探测。如 `MAME_BIN`、`SIMH_PDP8_BIN`。
- 语义：`os.environ.get(binary_env)` 指向真实二进制路径（46-A `_binary_path` 已实现）。

`binary_env` 解决的是"二进制不在仓库内"的场景——用户把 MAME 装在系统任意位置，只要设一个
环境变量，loader 就能找到它，无需把二进制复制进仓库（也符合"不随附二进制"红线）。

### 2.8 media_classes（介质类目支持表）

- 数组，元素须在 4.2 的八大介质类目内。
- 例：MAME apple2 支持 `["disk", "tape"]`（Apple II 软盘 + 磁带）；FC 支持 `["cartridge"]`。

`media_classes` 是槽位对"我能吃哪些介质"的声明，供 doctor 校验"用户放进来的介质是否这个槽位
能跑"。它同时也是前端"这台机器能玩什么"的提示来源。

### 2.9 license 三件套（槽位级）

**两种形态（向后兼容）**：

1. **三件套对象（推荐，生产槽位必选）**：

```json
"license": {
  "tier": "gpl-2.0-or-later | bsd-3-clause | mit | apache-2.0 | proprietary | cc-by | public-domain | unknown",
  "url": "https://...",
  "date": "2026-11-04",
  "doc": "licenses/MAME.md",
  "note": "版本需核实"
}
```

   三件套 = **分档（tier）+ 来源 URL + 获取日期**；`doc` 挂钩 `licenses/` 目录的许可说明文件，
   `note` 记"需核实"等状态。缺 `tier` / `url` / `date` 任一 → SV-04 FAIL。

2. **简写字符串（兼容，仅仓库自带/样例）**：`"license": "MIT（本仓库自带）"` ——
   用于仓库自带后端（无外部二进制、无外部分发义务）。SV-04 判定为非空即 PASS，
   但标注"简写，建议升级三件套对象"。

> 与 46-A 实现的衔接：46-A `resolve_entry` 把 manifest.license **对拷**到网关注册表
> `entry["license"]`。当 license 为对象时，loader 需序列化为可读字符串（`tier + url`）再对拷；
> 本规范要求 46-A 后续迭代补此转换（见附录 A 核对表 #4）。

许可三件套是槽位系统的合规护栏。模拟器（MAME/SIMH 等）各有自己的许可（GPLv2+、BSD、自定），
本项目主程序是 MIT 且与模拟器"独立进程 + 协议通信"隔离，所以运行不传染，但**分发二进制**就要
另作法律评估。三件套把"这个槽位的二进制什么许可、从哪来、何时核实"钉死在 manifest 里，防止
"许可不清的二进制混进仓库"。

### 2.10 capabilities（四能力位）

| 位 | 类型 | 含义 | 缺省 |
|---|---|---|---|
| `frame` | bool | 能出帧（视频） | false |
| `audio` | bool | 能出音频 | false |
| `input` | bool | 能接输入 | false |
| `save` | bool | 能存档 | false |

- 语义：声明该槽位的后端**能力上限**，供 launch/doctor 判定"真跑 vs 演示降级"。
- 例：fake 后端 `{"frame": true, "audio": true, "input": false, "save": false}`。

四个能力位是"演示降级"的判据来源。真实后端若只声明了 frame 没声明 audio，前端就该关闭声音
按钮；若 input 为 false，就该隐藏交互。它让引擎能在不逐个模拟器特判的情况下，统一做"能力
驱动的界面裁剪"。

### 2.11 keymap

- 键码表路径，缺省 `null` → 走 `keys/keymap_<machine>.json` 三级回退（keymap_register.md 不变）。
- 显式值仅在同后端有非默认机种名时使用（如 `keys/keymap_apple2.json`）。

### 2.12 完整示例（fake-slot 升级版，三件套对象）

```json
{
  "slot_id": "fake-slot",
  "device_class": "console",
  "backend_type": "native",
  "description": "样例槽位：演示 manifest → 网关自动注册（挂本仓库 fake 后端，无二进制要求）",
  "license": {"tier": "mit", "url": "https://opensource.org/licenses/MIT", "date": "2026-11-04", "doc": "licenses/MAME.md"},
  "media_classes": ["cartridge"],
  "capabilities": {"frame": true, "audio": true, "input": false, "save": false},
  "keymap": null
}
```

## 三、两大枚举全集

### 3.1 设备类目 device_class（7 项，全集）

| 值 | 含义 | 内容包 category 映射 |
|---|---|---|
| `computer` | 通用计算机 | early-computer / minicomputer / mainframe / personal-computer |
| `console` | 家用游戏机 | game-console |

`disk/` 目录，slot_check 会在 SV-03 直接 FAIL，而不是等到运行时才发现跑不起来。

## 四、媒体目录组织

### 4.1 嵌套规则

```
slots/media/<media_class>/<device_class>/<slot_id>/
```

- 三级嵌套固定：**介质类目 → 设备类目 → 槽位 id**。
- `<slot_id>` 必须与 `slots/emulators/<slot_id>/` 中的槽位一一对应（介质挂靠槽位）。
- 与 46-A 实现的核对：46-A 任务文曾写 `<device_id>`，但实现 `media_dirs()` 用 `<slot_id>`；
  本规范**定稿为 `<slot_id>`**（介质挂靠的是"哪个槽位"而非"哪个设备包"），见附录 A #3。

三级嵌套的每一级都在回答一个问题：第一级"什么介质"，第二级"什么设备"，第三级"哪个槽位来跑"。
这样"famicom 的卡带要用 mesen 槽位跑"就是路径 `media/cartridge/console/famicom/` 一句话的事。

### 4.2 空槽位 README 模板

每个空 `<slot_id>/` 目录须放一个 `README.md`，内容模板（防止空目录被 git 忽略 + 说明用途）：

```markdown
# slots/media/<media_class>/<device_class>/<slot_id>/

放置 <槽位名> 的介质（<media_class>）。本目录为占位：真实介质由用户自备并放入。

- 扩展名约定：<见 3.3 对应行>
- 红线：不下载、不随附（FR-E3）
```

空槽位 README 是"占位而不越权"的落地：目录结构先立起来（让目录契约可见、可被 git 追踪），
同时用 README 明确"这里只放用户自备介质，仓库不下载不随附"的红线语义。

## 五、安全与红线

### 5.1 红线（不可逾越）

1. **不下载**：任何工具/脚本不得自动下载二进制或介质（FR-E3）；
2. **不随附**：仓库不随附真实二进制、ROM/固件/镜像；
3. **许可隔离**：模拟器以独立进程 + 协议通信隔离，不链接不派生，主程序许可不受传染（见 licenses/MAME.md）。

这三条红线贯穿槽位系统始终。槽位系统提供的是"放东西的位置"与"声明东西的契约"，绝不提供
"东西本身"。这样既规避了二进制/ROM 的再分发法律风险，也把许可边界划清——MIT 主程序与外部
模拟器之间只有进程间协议，没有代码层面的链接与派生。

### 5.2 哈希清单格式（可选，sha256 行格式）

每个介质目录可放一个 `SHA256SUMS` 文件（可选），行格式：

```
<sha256 十六进制 64 字符>  <相对介质目录的文件名>
```

- 例：`c3ab8ff13720e8ad9047dd39466b3c8974e592c2fa383d4a3960714caef0c4f2  game.nes`
- 校验（SV-05）：每行须 `空格` 分隔的两列，第一列 64 位小写 hex，第二列非空文件名；
  格式非法 → FAIL。缺 `SHA256SUMS` 文件 → 跳过（可选项）。

哈希清单用于"介质完整性可核对"——用户自备介质后，可对照 SHA256SUMS 确认文件没损坏、没被
篡改。它是可选项，因为它依赖用户已获得介质文件才能生成；但对正式展项，建议都配上。

### 5.3 来源三件套（介质级）

介质目录的 `README.md` 或 `SOURCES.md` 须对每个介质文件登记**来源三件套**
（分档 + URL + 日期），与内容包 THIRD_PARTY 同构（v0.4 §8）：
`public_domain / cc / licensed / visual_reference_only / 原创` + URL + 日期。缺失 → SV-04 WARN。

介质级来源三件套是内容包 THIRD_PARTY 三件套在"介质"维度的延伸：内容包登记"文档/照片/手册"
来源，槽位系统登记"ROM/固件/镜像"来源，二者同构不同域，共同构成项目的完整权属台账。

## 六、与既有注册体系的衔接条款

### 6.1 与 EMULATORS 注册表的衔接

- manifest → 网关注册表条目由 `slot_loader.apply_slots(EMULATORS)` 完成，字段对拷：
  `slot_id`（键）、`desc`（← description）、`license`（← license）、`module`（← backend_type 映射）、
  `device_class`、`media_classes`、`binary_hint` / `binary_env` / `keymap`。
- **约束（46-A 实现不得偏离）**：`backend_type` 映射表必须与本规范 3.2 的 7 项枚举一致；
  `binary` 相对路径必须相对 `slots/emulators/<slot_id>/`；`license` 对象须序列化后对拷。
- 同名冲突：内置注册（`gw/gateway.py` EMULATORS 硬编码项）优先，槽位同名则跳过。

这条衔接条款是本规范对 46-A 实现的"硬约束"：装载器怎么把 manifest 变成注册表条目，字段名、
枚举值、路径基准都要按本章来，否则 slot_check（47-B）会与 slot_loader（46-A）打架。二者是
"裁判"与"执行"的关系——规范是裁判，装载器是执行，执行不得偏离裁判的判据。

### 6.2 与 keymap 注册的衔接

- `keymap` 字段为可选；缺省走 `keys/keymap_<machine>.json` 三级回退（keymap_register.md 不变）。
- 槽位声明的 `keymap` 若与三级回退冲突，**槽位显式声明优先**（同 46-A 语义）。

### 6.3 与内容包 runtime 的衔接

- 内容包 `runtime` 新增 `slot` 提示字段（仅提示不强制）：`slots: {emulator_class, media_class, bios_hint}`，
  由 46-B 的 `run_profile.py` 读取。本规范第七章给出 15 包的回填建议值。
- `runtime.emulator`（旧字段）与新 `slot` 的桥接：`emulator` 为内容线自行声明的后端名
  （mame/simh-pdp8/vice/...），`slot` 为规范化的槽位提示；二者并存，`slot` 优先于 `emulator`
  用于 launch 判定。

`runtime.emulator` 目前是内容线自由填写的后端名（有 `mame`、`simh-pdp8`、`vice`、`qedsac`、
`davidpsharp-baby` 等多种写法），口径不统一；`slot` 字段把它们归一为"槽位提示"（emulator_class
对应 backend_type、media_class 对应介质类目、bios_hint 对应固件提示），是后续 launch 一键启动
（46-B）的可靠输入。

### 7.1 回填执行建议（交 03/05 线，不改他线文件）

回填不是一次性全量动作，而应按"有没有可跑后端"分批推进，避免为静态展项造无意义的槽位：

- **第一批（已有规范后端）**：apple-ii（mame）、pdp8（simh）、famicom（mesen）、atari-2600
  （stella）——这四个 `runtime.emulator` 已能映射到规范后端枚举，应优先回填 `slot` 字段，
  使 launch_device 的"真跑"路径对它们可用；
- **第二批（专用后端，待模块化）**：commodore64（vice）、bbcmicro（beebem）、sega-md（blastem）、
  ibm5150（pc86box）、edsac（qedsac）、manchester-baby（davidpsharp-baby）——它们归 `dedicated`，
  回填 slot 时把具体模拟器名写进 description，等 01 线补专用后端模块后即可真跑；
- **第三批（静态/预留）**：edvac、eniac（静态展示，不声明 slot）、pdp11、vax11、system360
  （simh/dedicated 预留，等后端落地再回填）。

回填的字段形态统一为：`runtime.slot = {"emulator_class": <backend_type>, "media_class":
<media_class>, "bios_hint": <固件提示或 null>}`。回填完成后，15 包基线从 v0（全空）推进到
v1（按批回填），slot_check 的基线扫描可据此做"未声明 vs 已声明"的统计。

### 7.2 与门禁（pkg_registry / verify_all）的衔接

01 线门禁 `pkg_registry.py`（TASK-41A）按"缺 THIRD_PARTY/annotations/双网格目录合计 0 gltf 或
`.wip` 标记"判定 WIP。槽位系统上线后，门禁应增加一条"slot 一致性"检查：内容包若声明了
`runtime.slot`，则该 slot 的槽位类目必须存在（由 slot_loader 判定）；未声明 slot 的包记 INFO
而非 FAIL。这样门禁把"内容包契约"与"槽位契约"两条线缝起来，避免出现"内容包声明了不存在的
槽位"的悬空引用。此检查由 01 线 46-B 的 verify_all 落地，本规范只规定判据。

## 八、典型接入场景演练

本节用两个端到端场景，把前七章的字段与目录串起来，验证"零代码接入"是否真的成立。

### 8.1 场景一：接入 MAME 跑 Apple II（真实后端 + 外部二进制）

1. **写 manifest**：新建 `slots/emulators/mame-apple2/manifest.json`，字段如下——
   `slot_id: mame-apple2`、`device_class: computer`、`backend_type: mame`、
   `description` 写清"需用户提供 MAME 二进制"、`license` 用三件套对象（tier 记 GPLv2+/BSD 双许可，
   url 记 MAME 官网法务页，date 记核实日期，doc 挂钩 `licenses/MAME.md`）、`binary: "mame"`、
   `binary_env: "MAME_BIN"`、`media_classes: ["disk", "tape"]`、`capabilities` 四位全 true、
   `keymap: "keys/keymap_apple2.json"`。
2. **放二进制**：用户把 MAME 可执行文件放进 `slots/emulators/mame-apple2/mame(.exe)`，
   或设环境变量 `MAME_BIN` 指向系统里已装的 MAME。
3. **放介质**：用户把 Apple II 系统软盘镜像放进 `slots/media/disk/computer/mame-apple2/dos33.po`。
4. **生效**：网关启动时 `apply_slots(EMULATORS)` 扫到该槽位，注册键 `mame-apple2` 出现在
   EMULATORS 列表；doctor 显示"二进制就位 / 介质 1 份"；`launch_device --device apple-ii`
   一条命令真跑。

整个过程没有改任何网关 Python 代码——唯一的新东西是一个 manifest 文件与两个用户自备的文件。
这就是"类 Batocera"体验的形式化。

### 8.2 场景二：接入 FC 红白机（专用后端归 dedicated + 卡带介质）

1. **写 manifest**：`slots/emulators/famicom/manifest.json`，`backend_type: mesen`
   （Mesen 后端，预留位）、`device_class: console`、`media_classes: ["cartridge"]`。
2. **放介质**：`slots/media/cartridge/console/famicom/game.nes`。
3. **待办**：Mesen 后端模块尚未实现（`BACKEND_TYPE_MODULE["mesen"] = None`），loader 会跳过
   注册并打日志"暂无模块映射"——这是**规范内的预留行为**，不是错误；等 01 线实现 mesen 后端模块
   后，同一 manifest 无需改动即可自动注册。

这个场景演示了"规范与实现的解耦"：manifest 先立契约，后端后补实现，二者互不阻塞。

### 8.3 场景三：静态展示设备（不声明槽位）

ENIAC、EDVAC 这类无模拟器的静态展项，`runtime.emulator: none`，**不声明 slot**（回填建议表
#3/#4 为"不声明"）。它们只参与静态展示，不进入槽位系统；slot_check 的 15 包基线扫描会把它们
记为"未声明（静态/待回填）"，不算错误。

## 九、常见错误与纠正对照

| 错误 | 后果 | 正确做法 |
|---|---|---|
| manifest 缺 `slot_id` 或与目录名不符 | loader 用目录名兜底，键名漂移 | slot_id 必填且等于目录名 |
| `device_class` 写 `game-console`（内容包 category 值） | SV-02 枚举 FAIL | 用槽位枚举 `console`，映射见 §3.1 |
| `backend_type` 写 `vice`（专用模拟器名） | 枚举外值 FAIL | 归 `dedicated`，模拟器名记入 description |
| `license` 只写字符串 "GPL" 无 URL/日期 | 三件套不完整 | 用对象 {tier,url,date}，或简写字符串标明"本仓库自带" |
| `binary` 写绝对路径 `C:\emu\mame.exe` | 跨机复制失效 | 用相对槽位目录的文件名 + 多架构表 |
| 介质放错类目（`.nes` 放 `disk/`） | SV-03 扩展名 FAIL | 按介质真实类目放入对应目录 |
| `SHA256SUMS` 行少一列 | SV-05 FAIL | 每行"64 hex + 空格 + 文件名"两列 |
| 空槽位目录不放 README | 目录被 git 忽略、意图不明 | 按 §4.2 模板放 README |

这张表是 slot_check（47-B）反例测试的直接来源——反例就是把这些"错误"逐个构造出来，验证
SV-01~05 能命中。

## 十、FAQ（高频疑问与边界澄清）

**Q1：槽位系统与内容包是什么关系？会不会重复登记？**
不重复。内容包管"设备自身的契约数据"（模型、标注、运行时提示），槽位系统管"跑这台设备需要的
外部资产"（模拟器二进制、介质）。二者通过 `runtime.slot` 字段对接：内容包声明"我需要哪个槽位"，
槽位系统提供"那个槽位在哪、能不能跑"。一台设备可以没有内容包（纯命令行跑槽位），也可以有
内容包但没有槽位（纯静态展示）。

**Q2：为什么介质目录要三层嵌套，而不是像模拟器那样一层平铺？**
因为介质的"复用关系"不同于模拟器。模拟器后端可复用（一个 MAME 跑多台机器），所以平铺最省；
介质几乎不跨设备复用（苹果的软盘镜像不会给 PDP-8 用），所以用"类目/设备/槽位"三层把归属钉死
在路径上。路径即索引，省去了一张"介质 → 设备 → 槽位"的注册表。

**Q3：manifest 写错了会怎样？**
slot_check（47-B）在静态校验阶段就报错（SV-01~05），而不是等到运行时崩溃。这是"契约即裁判"
的落地：放错目录、写错枚举、许可三件套缺一项、哈希行格式坏，都会在入库/门禁阶段被拦住。

**Q4：后端模块还没实现（如 mesen/simh 预留位），现在能写 manifest 吗？**
能，而且应该先写。manifest 是契约，后端是实现，二者解耦。现在写 mesen 的 manifest，loader 会
因为 `BACKEND_TYPE_MODULE["mesen"] = None` 跳过注册并打日志"暂无模块映射"，这是规范内的预留
行为；等后端模块补上，同一份 manifest 无需改动即可自动注册。

**Q5：为什么要三件套（分档+URL+日期），简写字符串不行吗？**
三件套是权属合规的最小闭环：分档回答"什么许可"、URL 回答"许可文本在哪"、日期回答"何时核实"。
简写字符串（如 "MIT（本仓库自带）"）只在"仓库自带、无外部分发义务"时够用；一旦槽位指向外部
二进制，就必须三件套齐全，否则将来分发时说不清权属。

**Q6：用户把二进制放错位置怎么办？**
doctor 与 slot_check 的 SV-03 会探测二进制是否就位。放错位置（不在槽位目录、环境变量没指到）
会被判为"二进制缺失"，并给出指引（该放哪、该设哪个环境变量），而不是静默失败。

**Q7：介质是用户自备的，仓库怎么保证完整性？**
通过可选的 SHA256SUMS 哈希清单。用户获得介质后，可对照清单核对 sha256，确认文件未损坏、未
被篡改。仓库不提供介质本身，只提供"正确介质长什么样"的摘要，既合规又能校验。

**Q8：这套契约对手机线（06）之类的未来线也适用吗？**
适用。device_class 已预留 handheld/phone/pda，media_class 已预留 card/app_package/firmware，
backend_type 已预留 mobile。未来新线只需在既有枚举里选值 + 建目录 + 写 manifest，不用改规范。

## 附录 D：设计决策记录（裁决与理由）

本附录记录本专章的关键裁决，作为未来 v0.5 正式版回溯的锚点。每条都写"选了谁、为什么、代价是什么"。

**D1：后端类型吸收 `native`（6 → 7 项）**。47-A 任务给的枚举是六项（mame/simh/stella/mesen/
mobile/dedicated），但 01 线 46-A 的样例槽位 fake-slot 用了 `native` 表达"仓库自带、零外部二进制"。
本规范选择**吸收 native**，因为 fake/demo 槽位是"演示降级"链条的第一环，必须有一个表达"这是
仓库自带后端"的枚举位；代价是枚举多一项，但换来"零二进制槽位"的可声明性。这一裁决体现了
"实现先行、规范收编"的协作顺序——合理且更成熟的实现产物，规范应予吸收而非退回。

**D2：介质目录第三级定为 `slot_id` 而非 `device_id`**。46-A 任务文曾写 `slots/media/<class>/
<device_class>/<device_id>/`，但实现的 `media_dirs()` 用的是 `<slot_id>`。本规范采纳实现口径，
因为介质挂靠的本质是"哪个槽位来跑它"，而不是"哪个设备包声明它"；同一设备可能有多个槽位
（如 apple-ii 既有 mame 槽位又可能有专门的磁盘槽位），用 slot_id 才能表达"这份介质给哪个后端"。
任务文的 `device_id` 记为笔误。

**D3：许可字段采用"三件套对象 + 简写字符串"双形态**。三件套对象是权属合规的完整登记，简写
字符串是给仓库自带/样例槽位的轻量形式。之所以保留简写，是因为 fake-slot 这类"仓库自带、许可
就是 MIT 一句话"的槽位，硬套三件套（tier+url+date）反而不自然；但生产槽位（外部二进制）必须
三件套齐全，这是红线。双形态让"样例轻、生产严"各得其所。

**D4：专用后端统一归 `dedicated` 而非逐一命名**。VICE（C64）、BeebEm（BBC）、BlastEm（MD）、
PC-86（IBM 5150）等在现有 15 包里出现了至少四种专用后端名。本规范先把它们统一归到 `dedicated`
一个枚举位，专用后端名记入 description 与 binary 字段；是否拆分为逐一命名留待开放问题。这样做的
理由是：逐一命名会让枚举随"接了多少专用模拟器"无限膨胀，而 `dedicated` + binary 已能表达全部
信息，命名膨胀的收益远小于维护成本。

**D5：capabilities 缺省全 false**。四个能力位缺省全 false，意味着"不声明能力 = 不承诺任何能力"，
前端据此裁剪界面、launch 据此判定是否降级。缺省 false 而非 true 的原因：宁可保守地少承诺，
也不要在后端其实不支持存档时让前端误开存档按钮。

这些裁决的共性：**当实现与规范冲突时，优先吸收"更成熟、更贴近真实语义"的一方，并把理由
写进裁决记录**，而不是机械地以某一方为准。

## 结语

槽位契约章要回答的，归根结底是一句话：**一台设备要"真跑起来"，除了内容包，还需要哪些外部
资产，它们该以什么契约组织、以什么方式校验**。本章给出的答案是——一份 manifest 声明后端与
许可、三层目录承载介质、五个校验规则做裁判、一个装载器做执行。它把"类 Batocera 的即插即用"
从体验口号变成了可执行、可校验、可跨线协作的工程契约。

需要特别强调的是，本章自始至终贯彻了"立法不越权"的原则：它只规定 manifest 的字段、目录的
嵌套、许可的登记与校验的判据，绝不替 01 线实现装载器、不替 03/05 线回填字段、不替用户下载
任何二进制或介质。规范与实现、规范与内容的边界，正是多线并行不打架的根基所在。

后续的推进路径清晰：47-B 落地 slot_check 校验器与 15 包基线；01 线 46-B 落地 launch 一键启动
与门禁 slot 一致性；03/05 线按第七章建议分批回填 slot 字段；待这些闭环后，本草案升版为 v0.5
正式章并入《内容包规范》正文，并据此更新内容包的 `meta.spec_version` 语义与配套 schema。
