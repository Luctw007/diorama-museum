## 一、分档依据与公共底线

### 1.1 分档对象

第二批候选 31-60 名单（03 线 173-A 产出）：**S 档 8 / A 档 12 / B 档 10，共 30 台**，均不与 30 台
定案表重复。样板 = 第二批首台 **nokia-3310**（已产、84 PASS / 0 FAIL、已反链 done、已入每日门禁
`pkg:nokia-3310`）。

### 1.2 公共底线（三档共同硬底线，分档不降低）

> **分档只区分"生产深度"，不降低门禁底线**——三档只要"进 ready"，就必须过同一套硬底线：

| # | 硬底线 | 依据 |
|---|---|---|
| 1 | `validate.py` 0 FAIL | `CONTRIBUTING` §四自测口径 |
| 2 | `catalog_ref_check` REF 四查 0（REF-01 悬空 / REF-02 反链 / REF-03 台账 / REF-04 形态） | `规范增补_v0.6.2` §六反链义务 |
| 3 | THIRD_PARTY 三件套（分档 + URL + 日期） | `内容包规范_v0.4` §8 |
| 4 | id 唯一（`id_registry allocate` 申请，不手编） | `内容包与目录规范_v0.6` §一 |
| 5 | 反链义务 REF-02（完工过闸回填目录 `device_id` + `status=done`） | `规范增补_v0.6.2` §六 |

### 1.3 三档一句话定位

- **S 档（镇馆级）**：全规格深做，逼近定案表 30 台的规格。
- **A 档（标准展示）**：近似 S 但"需核实"字段从宽、标注以 role 为主、百科字数下限略低。
- **B 档（名录/轻展示）**：最小可展示 + 静态/动画，`emulator="none"`，百科可存缺口。

### 1.4 分档设计原理

分档的出发点是 00 基线「决策 1」的分级路线结论：台台全规格成本不可行（约 1500-4500 积分/台），
只能"镇馆之宝全规格 + 标准展示 + 名录级"三档分级。三档的差异**只在生产深度**——S 档把建模、标注、
百科、可运行都做满，A 档在标注与百科上留一点余地，B 档只保"能摆出来看"。但三档共同守住一条线：
**只要进 ready，就必须 0 FAIL**。这样既控制了总积分，又不让"名录级"成为"低质量放水"的借口——
门禁对三档一视同仁，档位只决定"做多少"，不决定"做多差"。

> 对 03/05 线的实操含义：一台设备先从 B 档"最小可展示"起步（成本最低、最快进 ready），后续有预算
> 再补件升 A/S 档；升档不重发 id、不重验底线，只做增量补件——这是"先占位、后加深"的滚动生产节奏。

## 四、B 档（名录/轻展示，10 台）验收口径

| 项 | 口径 | 与 S/A 差异 |
|---|---|---|
| 件清单 | meta/runtime + ≥1 gltf + THIRD_PARTY + 明确 `emulator="none"`（静态+动画） | 最小可展示 |
| 校验 | `validate.py` 0 FAIL（硬底线不变） | 同 S |
| encyclopedia | 可存缺口（`pkg_registry` 进 NOTE 转补，不判 WIP） | 可留缺口 |

## 五、WIP 分级升档规则

### 5.1 逐态定义

| 态 | 定义 | 门禁语义 |
|---|---|---|
| `planned` | 已列名单、未动工 | 目录侧占位 |
| `researching` | 调研中、未开产 | 目录侧占位 |
| `package` | 已开产、有目录 device_id 关联、结构未齐 | 目录侧在产 |
| `wip` | `.wip` 标记文件，或结构性半成品（缺 THIRD_PARTY / annotations / 0 gltf） | `pkg:*` 只提示、不进失败判定 |
| `done` | 全部硬底线过闸、已反链 | `pkg:*` 进 ready 全绿 |

### 5.2 升档判据（`.wip → 补件 → ready → done`）

1. **`.wip` 是什么**：包内根目录放 `.wip` 标记文件 = "生产中的显式声明"，交付时删除。`_is_wip` 判据
   三选一：存在 `.wip` 文件 / 缺 `THIRD_PARTY.md` 或 `annotations/annotations.json` / 两网格目录合计
   0 个 gltf。
2. **何时删 `.wip`**：结构性件（meta/runtime/THIRD_PARTY/annotations + ≥1 gltf）齐备后删除 `.wip`，
   但 encyclopedia 可后补（缺不算 WIP）。
3. **何时进 ready**：删 `.wip` 且 `validate.py` 0 FAIL + REF 四查 0 后，`pkg_registry` 自动判 ready
   （无 `.wip`、结构件齐、≥1 gltf）。
4. **何时回填反链**：进 ready 后回填目录 `device_id` + `status=done`，过 `catalog_ref_check` REF-02；
   未回链 = REF-02 反链缺失，门禁 FAIL。
5. **升档路径**：B 档升 A/S 档 = 补件（encyclopedia / flow 标注 / 全 assemblies），不重发 id、不重验
   底线，只做增量补件后重跑 validate。

### 5.3 样板走查：nokia-3310 的过闸路径（供 03 线照抄）

第二批首台 nokia-3310 是"从取件到 done"的完整样板，其路径可复刻到其余 29 台：

1. **取件申请 id**：从 173-A 名单占位 `M-MP-0000xx` → 向 `id_registry allocate` 申请真实 id
   `M-MP-000015`（nokia-3310 实得号）。
2. **生产件清单**：meta（id=nokia-3310 / era=2000 / category=phone）+ runtime（emulator="none" 演示向，
   预留 Symbian/MAME 手持）+ assemblies ×6 + annotations 33 条（flow 10 + role 23）+ encyclopedia
   2,548 汉字 + THIRD_PARTY 三件套。
3. **过闸**：`validate.py` 84 PASS / 0 FAIL；`catalog_ref_check` REF-01~04 全 0。
4. **反链**：目录 `通讯与移动大类_目录_v3.jsonl` 里 `M-MP-000015` 的 `status: researching→done`、
   `device_id: null→nokia-3310`。
5. **入闸**：`pkg:nokia-3310` 进每日门禁（ready 31 包之一）。

> 样板的意义：它证明"B 档口径（emulator="none" 静态 + 最小件 + 百科齐）也能过闸"，为其余 B 档
> （Manchester Mark 1 / Whirlwind / IBM 701 / HP 2100 / Osborne 1 / Compaq Portable / TI-99/4A /
> Newton / Palm III / BlackBerry 850）提供了可直接参照的模板。

## 七、常见问题（FAQ）

**Q：B 档 `emulator="none"` 会被当成"没做完"吗？**
A：不会。`emulator="none"` 是"静态 + 动画演示"的**显式声明**，不是半成品；它对应 `runtime.emulator`
的合法取值，校验器不会因此报 FAIL。真正判定"没做完"的是 WIP 判据（`.wip` / 缺 THIRD_PARTY /
缺 annotations / 0 gltf），与 `emulator` 取值无关。

**Q：encyclopedia 缺了要不要紧？**
A：缺 encyclopedia **不算 WIP**，`pkg_registry` 会记 `[NOTE 缺 encyclopedia.md]` 转内容线补齐，
不进失败判定。但 S 档按口径应把 encyclopedia 做全（它是"镇馆级"的组成部分），B 档才允许"存缺口
转补"。

**Q：一台设备先做 B 档，之后想升 S 档怎么办？**
A：不重发 id、不重验底线。只需增量补件（encyclopedia 补全 + flow 标注 + 全 assemblies 补满），
补件后重跑 `validate.py` 0 FAIL 即可；目录 `device_id` 与 `status=done` 不变，反链义务不重复执行。

**Q：第二批的 id 什么时候分配？**
A：本口径**不分配 id**。正式生产时由 03 线按 `id_registry allocate <大类码> <数量> <中分类码>` 申请
真实 id（名单里的 `0xx` 是占位符），再由 01 线登记 + 用户点头，才进入第二批定案。

**Q：分档会不会让 B 档设备"低质量"进 ready？**
A：不会。三档的硬底线（validate 0 FAIL / REF 四查 0 / THIRD_PARTY 三件套 / id 唯一 / 反链 REF-02）
完全相同，分档只决定"做多少件"，不决定"底线高低"。B 档的"最小件"也必须 0 FAIL 才进 ready。

## 八、口径边界与未覆盖项

本口径是"验收口径"不是"第二批定案"，边界如下：

- **不定案**：30 台候选是否正式列入第二批，仍走"01 线登记 + 用户点头"两步，本口径不代决定。
- **不分配/登记 id**：`0xx` 占位符由 03 线生产时走 `id_registry allocate` 换真号，本口径只规定"必须
  申请真号、不得手编"。
- **不改门禁**：本口径只描述"三档如何对应现有门禁步骤"，不新增/修改 `verify_all` / `pkg_registry` /
  `release_check` 任何脚本；若后续要新增"真跑阈值 ≥5"等断言，属 01 线任务，另行立项。
- **不否决存量**：口径不得导致存量 31 台包（含 nokia-3310）回退为 FAIL，不得以 S 档标准反手要求
  已过闸的存量包升级；三档硬底线与存量包现行底线一致。
- **未覆盖项**：家电影音类第二批（归属 05 线，见《家电影音开题 v1》）不在本口径覆盖内；真跑矩阵
  阈值上调（≥5 台）与 `run_status` 字段的落点，转 v0.7 章 D 与 01 线 release_check 后续任务。
