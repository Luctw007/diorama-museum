## 二、公共资产的变更流程

### 2.1 内容包字段变更（schema/校验器受影响时）

```
内容线提出字段需求 → 02 线规范先行（升版规范草案 → 评审）→
02 线改 schema + validate（含反例）→ 各内容线按迁移表升级内容包 →
01 线改 loader/桥（如 input_map 键名）→ 全量回归（regress_all 0 FAIL）
```

- **顺序铁律**：规范先行，schema/校验器与内容包同轮改，内容线不得在规范未定时擅自加字段。
- **同轮改铁律**：schema/validate 与受影响内容包**同一轮**改完并回归，禁止 schema 先改而内容包
  隔轮再迁（否则中间态回归红灯、责任不清）。

### 2.2 网关注册与键码表主权（01 线）

- 模拟器注册、`input_event` 键名（`KEY_*` → 键码翻译层）、键码映射表主权归 **01 线**。
- 内容线在 `input_map` 里使用的键名（含 `KEY_*`、项目扩展键 KEY_POWER/KEY_RESET/KEY_REPEAT）须
  遵守 02 线规范 §11.2 全集表；新增键名须 02 线规范先行 + 01 线翻译层跟进。

### 2.3 变更流程 worked example（以 input_map 对象化为例）

```
① 05 线 apple-ii 用对象格式 {map,key}（契约漂移，DEFECT-M1B-KEYMAP-01）
② 02 线规范 v0.2.1 §11.2 裁决：对象格式为唯一新格式、legacy 为兼容窗口
③ 01 线 run_profile 支持对象格式（保留旧字符串兼容）
④ 03 线黎明厅四包按迁移表对象化（legacy 移除触发点跟踪）
⑤ 02 线 regress_all 全量回归 0 FAIL
```

> 该流程完整落地了"规范先行 → 引擎跟进 → 内容迁移 → 回归验证"四步，是后续字段变更的标准模板。
> 当前进度：①②③⑤ 已闭环，④（03 线四包对象化）仍在 legacy 移除触发点跟踪中。

### 2.4 变更的回归门禁

任何公共资产变更（schema/validate/PROTOCOL/键码表）合入前必须过门禁：

| 门禁 | 命令 | 通过标准 |
|---|---|---|
| 校验器自测 | `python tools/validate/tests/run_tests.py` | FAIL 0 |
| 建模校验自测 | `python tools/validate/tests/run_model_tests.py` | FAIL 0 |
| 全包回归 | `python tools/regress/regress_all.py --with-model` | 全部 FAIL 0 |

> 变更若导致任何存量包从 PASS 回退到 FAIL，须先给存量包打补丁或回退变更（与 v0.3 建模章的
> "R-090 强化前先核对占位盒"同一条红线）。

### 2.5 变更的回退与撤销

- 变更合入后若发现破坏（回归红灯/契约冲突），**先回退变更恢复绿**，再排查根因，禁止"带病推进"。
- 回退动作：revert 到变更前版本 + 全量回归确认 0 FAIL；回退记录写入完成报告"迭代记录"节。
- 禁止用"临时豁免""跳过某包"掩盖回退（除非走 §三 冲突处置的显式裁决）。

## 三、冲突处置

### 3.1 裁决优先级（同文件被两线产物占据时）

| 优先级 | 主权 | 说明 |
|---|---|---|
| 1 | **规范**（02 线 spec/schema） | 最高，字段/命名/格式以规范为准 |
| 2 | **引擎契约**（01 线 PROTOCOL/键码） | 运行时契约 |
| 3 | **内容**（03/05 线 content） | 内容数据 |
| 4 | **设计文案**（04 线 design） | 文案/验收 |

### 3.2 处理模板（退回 / 吸收 / 改名三选）

1. **退回**：越界产物撤回，由主权线重写（适用：内容线擅自改 schema、规范未定义字段）。
2. **吸收**：越界但合理的产物，由主权线正式吸收进规范/契约（适用：05 线 19/20 冻结表被 02 线 v0.3 吸收）。
3. **改名**：命名冲突时，非主权方改名让位（适用：narr_ → vo_、bgm_hall_dawn → bgm_dawn_01）。

**三选的分辨法**：

| 判断 | 处置 | 后续 |
|---|---|---|
| 越界产物违反规范硬约束（字段/格式/命名非法） | 退回 | 主权线重写，越界方撤销 |
| 越界产物合理且更成熟（量级/惯例有据） | 吸收 | 主权线升版规范收编，附裁决记录 |
| 越界仅命名冲突（前缀/序号与规范不符） | 改名 | 非主权方改名为规范命名，留回写建议 |

### 3.4 冲突处置记录模板

每次冲突处置须在对应完成报告"裁决记录"节按下列模板记录，缺一不可：

```markdown
| # | 冲突点 | 甲方产物 | 乙方产物 | 裁决 | 理由 |
|---|---|---|---|---|---|
| N | <冲突对象> | <越界方产物> | <主权方产物> | 退回/吸收/改名 | <规范>线内文档 的裁决依据 |
```

> 记录的价值：让后续轮次能追溯"为什么这么定"，避免同一冲突反复裁决。

> 处置记录须写入对应完成报告"裁决记录"节，并附理由（规范 > 线内文档为准绳）。

### 3.3 冲突处置实例集（历史 4 例，供参照）

| 实例 | 冲突 | 处置 | 结果 |
|---|---|---|---|
| 05 线 19/20 冻结表 | 05 线自行定义三档 LOD/材质 | **吸收** | 02 线 v0.3 吸收其量级，裁决 6 条 |
| 04 线 narr_/bgm_hall_dawn 命名 | 与规范 vo_/bgm_厅_序号 冲突 | **改名** | 02 线 v0.4 裁决 vo_/bgm_dawn_01 |

## 五、「需核实」标记的行为统一

### 5.1 标注内容

- 标记词统一：`需核实`（中文）/ `[待核实]` 不混用；禁止在**正式文案**（`text`/`role.zh`/`caption`/
  `intro.zh`/解说稿正文）出现未定标记（R-060/083 红线）。
- 允许出现位置：调研/预研文档、任务文档、完成报告的"开放问题"节。

### 5.2 汇总表归属

- 各线的「需核实/开放问题」汇总表归本线 `docs/`（如 05 线 `docs/research/apple-ii/15_开放问题与待核实汇总.md`）。
- 02 线规范附录 B 汇总**跨线**开放问题（跨线跟踪点）。

### 5.3 解除条件

- 解除须满足：**行级引用**（标注具体来源编号 [Sxx] 或文件路径）+ **审查人确认**（对应主权线审查）。
- 解除后在汇总表把状态由「待核」改「已核-<结论>」并回填日期，不留悬空。

### 5.4 「需核实」示例（正反）

| 场景 | 正/反 | 说明 |
|---|---|---|
| 调研文档写"许可待核（Freesound 待页面核验）" | 正 | 未核实就标待核，属 §5.1 允许位置 |
| 正式 meta.json 的 `role.zh` 写"具体参数需核实" | 反 | 正式文案出现未定标记，触发 R-060/083 |
| 完成报告"开放问题"列"TTS 取舍待裁决" | 正 | 遗留项入开放问题，合法 |
| 索引表"字段齐备"列写"缺 intro/era" | 正 | 客观事实陈述，非未定标记 |

### 5.5 「需核实」与校验红线的衔接

- R-060（标注）/R-083（caption）在**正式文案**里禁止未定标记，是本契约 §5.1 的机器化落地——
  契约管"人"，校验器管"文件"，二者同一条红线。
- 若某线的调研文档需要引用尚未核实的结论，写在"开放问题/待核实汇总表"，**不得写进正式文案**；
  正式文案若有未定标记，`validate.py` 直接 FAIL，不因"待核实"而豁免。
- 跨线引用的未核实结论，引用方须注明"来源线 + 状态待核"，不得当作已核实事实转写进自己的正式文案。
