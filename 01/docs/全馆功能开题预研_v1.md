## ① 多厅加载方案：单场景多厅 vs 分场景加载

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A 单场景多厅（现状四厅并存于主场景） | 切换零加载、展览动线连贯、HUD/图鉴/真跑全局状态不中断；与现 exhibit_host 四厅布局+switch_hall 直接续用 | 顶点/材质预算全厅常驻，40+ 台后单机 GPU/内存压力上升；拆解 L0-L3 高精度与远景同场景需 LOD 纪律 | **建议 v1.0 采用 A（延续现状）**，按台本将四厅扩展为「大厅 + 四子厅」仍单场景；内存红线另设「设备实例预算表」（见 ④排期 F-4） |
| B 分场景加载（厅级 PackedScene） | 单厅预算独立、超大规模可扩展 | 切换有加载帧、全局状态（图鉴索引/真跑进程/口播轨）需跨场景携带，复杂度高 | 仅当单厅台数超预算（如 >20 台/厅）时再启用，作 1.x 后备 |

取舍理由：v1.0 判据 30 台四厅，平均 7-8 台/厅，单场景可承受；ROADMAP「镇馆之宝可跑」要求真跑进程跨厅存活（MAME/SIMH 独立进程不受场景影响），单场景方案最稳。

## ② 房间切换口径（门/传送点/大厅映射，与 exhibit_layout_spec 对齐）

- 采用 **大厅（Hub）映射 + 传送点**，非门缝走门：大厅为四厅入口动线枢纽（沿用 04 线 03 号
  「一眼可见、三步可达」原则），各子厅入口设传送点（layout 扩展 `portal` 条目，位置/朝向
  沿用 L-03 坐标规则 + 04 线朝向角转换公式 `rotation.y = deg_to_rad(-朝向角)`）。
- 切换语义沿用 TASK-114/171-B 已落地件：ExhibitHost.switch_hall 清场重建 + 运行配额保留 +
  调试圈记忆；HallNavPanel（M/N/P）作为大厅映射 UI 底座，新增「大厅总览面板」列四厅与
  镇馆之宝入口（图鉴 Tab 联动）。
- layout schema 扩展提案（待 02 线规格同步）：`portals: [{target, position, rotation}]`、
  `hall_group`（大厅/子厅分组）、`lod_scale`——本预研只提口径，不落 layout 文件。
- 与拆解深度衔接：拆解观察区与整机展示位「分离」（04 线 03 号决策），房间切换不打断拆解
  会话——L2/L3 高精度设备在「工作台」子区呈现（depth_model L0-L3 按台分批加载）。

## ③ 与拆解 / 图鉴 / 真跑三系统的衔接点

| 系统 | 衔接点 | 口径 |
|---|---|---|
| 拆解 | 房间切换时清场重建会释放设备实例 | switch_hall 前若处于拆解会话：先 exit_explode → 保留「最近拆解台」状态，回厅可续（待实装验证）；工作台区 L2/L3 分批加载（depth_model 预算） |
| 图鉴 | 大厅映射与图鉴索引同源 | exhibit_index.json 六厅映射（181-A 收口）即大厅动线数据层；HallNavPanel 与 EncyclopediaPanel 共用「厅 → 设备」视图，避免第二套清单 |
| 真跑 | 真跑进程跨厅存活 | 网关独立进程（ADR D1），切厅不杀；启动器 launch_device 按设备 id 定位，与厅无关（216-B 已证）；「可玩台」在大厅有专属标记（slot 真跑机种 ≥5 判据展示位） |
