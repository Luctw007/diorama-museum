## 一、总则与适用范围

### 1.1 目标

在正式 3D 建模开产之前，把"网格怎么组织、预算怎么定、材质怎么贴、占位盒怎么换"这四件事写成
可执行的规则，避免各内容线各自为政、产出互不兼容的资产，避免返工。本章服务的对象是四可标准里
依赖网格质量的"可看、可拆、可懂"三档：外观展示（可看）、拆解展示（可拆）、原理讲解（可懂）。

### 1.2 适用对象

- 所有内容包的 `assemblies/` 与 `meshes/` 下的 glTF 网格资产；
- 网格所引用的 PBR 纹理（basecolor / metallic-roughness / normal / emissive）；
- 占位盒 → 正式模型的替换过程（含 `meta.json` 的 `mesh_ref` 引用一致性）。

### 1.3 基本原则

1. **1 装配体 = 1 文件**：网格按装配体拆分，节点命名即契约（R-090 延续），让 loader 按 id 定位
   节点零成本；
2. **预算先行**：面数、节点、纹理尺寸三预算按档给数字，超限不阻塞但必须可见（沿用 v0.2.1 §5
   的"可调不阻塞"原则，但正式网格要当真）；
3. **增量交付**：占位盒能跑起来的前提下，正式资产按"外观 → 内部蒙皮 → 内部结构"逐级替换，
   任何一步替换都不许改 loader、不许改 `meta.json` 的节点 id 与 `mesh_ref`（除扩展名同步）；
4. **写实优先**：复古设备走写实 PBR 管线，以实物/展项照片为参照人工重建，不贴版权素材。

### 1.4 术语定义

| 术语 | 定义 |
|---|---|
| node_id | `assemblies[].id` 或 `components[].id`，snake_case，全局唯一 |
| mesh_ref | 装配体引用的 glTF 相对路径（`meshes/<id>.gltf`） |
| 占位盒 | 现阶段的单位三角形占位 glTF，节点名 = node_id，不伪造复杂几何 |
| LOD | Level of Detail，按观察距离切分的网格精度档位 |
| PBR | Physically Based Rendering，金属度-粗糙度物理渲染管线 |
| 完整性三档 | 外观 / 内部蒙皮 / 内部结构，同一装配体的增量交付阶段 |
| 距离三档 | LOD0 特写 / LOD1 观察 / LOD2 远景，按观察距离切分 |

## 二、网格组织

### 2.1 一个装配体 = 一个 .gltf 文件

- 装配体（`assemblies[].id`）若声明了 `mesh_ref`，则其网格为一个独立的 `.gltf`（或 `.glb`）文件，
  文件名为 `<assembly-id>.gltf`，存放于 `meshes/` 或 `assemblies/` 目录（沿用 v0.2.1 §2 目录结构）。
- **一个文件只描述一个装配体的几何**。允许一个 glTF 内含有多个 `mesh`/`node`（例如一个机箱的
  上盖、底壳、铭牌、提手等多个子网格合并进同一文件），但**场景根节点必须唯一**，且其 `name`
  等于该装配体的 `node_id`（R-090 延续）。
- 元器件（`components[]`）默认**不单独成文件**，而是作为其所属装配体 glTF 内的子节点
  （`node.name = component.id`），随装配体一起交付；只有"明星件"（如 6502 CPU、晶振、扬声器）
  需要近距离特写时，才允许拆分为独立 mesh 引用（见 §3 特写档）。

> 现状核对：当前占位盒已满足"一装配体一文件 + 根节点名=node_id"。正式建模不得破坏这一约定。

### 2.2 节点命名 = node_id（R-090 延续）

- glTF 场景根节点 `name`（以及根 `mesh` 的 `name`）必须等于该装配体的 `node_id`，供引擎按 id 做
  高亮、拆解动画与点选定位。这是 v0.2.1 R-090 的既有要求，正式网格**沿用且强化**（见 §8）。
- 装配体内部的子网格节点命名遵循 `<assembly-id>_<子部件>` 的 snake_case，例如 `case_lid`、
  `case_bottom`。子节点名不是 loader 契约（loader 不依赖），但要求可读、同文件内唯一。

**为什么根节点名必须是 node_id**：引擎的定位逻辑是"按 `meta.json` 里的 `mesh_ref` 找到文件，
再按 `node_id` 在文件里找到根节点"来装配、高亮、播放动画。若根节点名与 node_id 不一致，引擎
要么找不到节点（装配失败），要么做一次脆弱的字符串映射（易漂移）。历史上 edsac 的
`control_subsystem` 引用 `console.gltf`（节点名 `console`）正是这类事故（已在 TASK-18A 修复）。

### 2.3 同一装配体的三档完整性（外观 / 内部蒙皮 / 内部结构）

针对"增量交付"，一个装配体的建模按**完整性**分三档递进，允许分阶段提交：

| 完整性档 | 含义 | 包含内容 | 适用场景 |
|---|---|---|---|
| **外观（外观壳）** | 只做外表面 | 外壳可见面，无内部、无背面 | 整机远景、外观展示（"可看"起步） |
| **内部蒙皮** | 外观 + 内表面 | 外壳 + 打开后的内壁、舱体、屏蔽罩 | 开盖/开门后的内部观察 |
| **内部结构** | 全内部 | 内壁 + 内部板卡、元器件、线缆、机构 | 拆解/爆炸图（"可拆/可懂"） |

> 约定：外观档的面数最少（预算见 §3 远景/观察档）；内部蒙皮次之；内部结构档使用最高面数预算
> （§3 特写档）。三者是**同一个 node_id 的增量替换**关系，而非三套并存的 LOD 文件——即生产阶段
> 先提交外观壳，后续补内部结构时**替换同名文件**（见 §7 替换协议）。

### 2.4 多节点文件 vs 单节点文件的取舍

一个 glTF 文件内部"把子部件拆成多个 node"还是"合并成一个 mesh"，遵循以下取舍：

- **多 node 拆分**：子部件需要独立高亮/动画/点选时拆（如键盘的 52 颗键帽各成一个 node）；
- **合并 mesh**：子部件永远一起出现、无需单独操作时合并（如去耦电容组、RAM 三行插座）。
- 取舍依据是"**运行时是否需要单独寻址**"，而不是"建模方便"。若合并后仍需单独高亮，就只能
  走"拆 node"路线，事后拆分成本高，故建模前先定好。

### 2.5 命名规范详表（目录/文件/节点/材质/纹理）

本章把网格相关的一切命名统一成一张表，作为 v0.2.1 §4 命名规范的网格侧延伸：

| 对象 | 命名 | 示例 | 约束 |
|---|---|---|---|
| 装配体网格文件 | `<assembly-id>.gltf` / `.glb` | `case.gltf` | 与 `mesh_ref` 一致 |
| 装配体根节点/根 mesh | `<assembly-id>` | `case` | = node_id（R-090） |
| 子网格节点 | `<assembly-id>_<子部件>` | `case_lid`、`mainboard_cpu` | snake_case，文件内唯一 |
| 元器件网格文件 | `<component-id>.gltf`（明星件才拆） | `cpu.gltf` | 可选 |
| 材质 | `<node_id>_mat` 或材质功能名 | `case_abs`、`pcb_fr4` | 可复用，跨文件共享 |
| 贴图 | `<node_id>_<map>.png` | `case_basecolor.png` | map ∈ basecolor/metallic_roughness/normal/emissive |
| 目录 | `meshes/`、`assemblies/`、`materials/` | — | 沿用 v0.2.1 §2 |

> 命名统一的价值：loader 按 `node_id` 定位、校验器按命名正则扫描、budget_check 按后缀识别 LOD，
> 三处都依赖"命名即契约"，故建模阶段就必须遵守，事后改名成本极高。

## 三、顶点与三角形预算三档表

### 3.1 三档定义（按观察距离）

正式网格按**观察距离**分三档 LOD。命名采用 Godot 4 惯例（**LOD0 = 最高模/最近**，索引越大越远越低）：

| 档位 | 观察距离 | 别名 | 单装配体三角面 | 整机三角面 | 纹理上限 | 主要用途 |
|---|---|---|---|---|---|---|
| **LOD0 特写档** | < 0.5 m（点选/拆解特写） | 高模 | ≤ 20,000 | ≤ 200,000 | 4096 px | 拆解级展示、明星件特写（"可拆/可懂"） |
| **LOD1 观察档** | 1–2 m（展台正前方） | 中模 | ≤ 2,000 | ≤ 20,000 | 2048 px | 默认交付（"可看"主力档） |
| **LOD2 远景档** | > 3 m（展厅全景/过道） | 低模 | ≤ 200 | ≤ 2,000 | 512 px | 远景兜底，引擎自动切换 |

> 与 v0.2.1 §5 精度分级（L1–L4）的关系：**LOD1 观察档 ≈ 精度级 L2（默认交付）；LOD0 特写档 ≈
> L3；LOD2 远景档 ≈ L1**。`meta.precision_level` 仍是"整机目标档"的权威声明；本章的"三档 LOD"
> 是**单台设备内部、按距离切分**的网格档位，二者正交、可叠加。正式交付时，内容包应至少提供
> 其 `precision_level` 对应档位（默认 L2 → 观察档），远景/特写档按需提供。

### 3.2 具体数字依据（Godot 4 + 中端 VR 硬件系数）

本表的数字依据如下，供评审调整：

1. **中端 VR 硬件基线**：Quest 3 / Pico 4 一类头显的 GPU 吞吐约 4–6M 三角面/帧 @ 72–90Hz。扣除
   场景灯光、天空盒、地面、其它设备与 UI 后，**单台设备的全展开三角面预算约 ≤ 200 万**，
   即 LOD0 整机 200,000 三角面是保守可行的；一个展厅同屏 3–5 台设备时仍能留出约一半余量。
2. **距离平方衰减**：从 0.5 m（特写）拉到 3 m（远景），设备在屏幕上的投影面积约缩小为 1/36。
   按"面数与投影面积正比"的常见 LOD 经验，远景档取特写档的约 1/100（200,000 → 2,000）足够。
3. **单装配体拆分粒度**：LOD0 特写档单装配体 ≤ 20,000 三角面，与现行 L3"单模型 200,000"保持
   一致量级（允许一台整机拆成约 10 个 ≤20,000 的装配体）；LOD1 观察档单装配体 ≤ 2,000，对应
   L2"单模型 20,000"把整机拆成约 10 个装配体后的均值。
4. **纹理系数**：与 v0.2.1 §5 一致（512/2048/4096），特写档允许 4096 供明星件贴图，远景档 512
   兜底，与 `budget_check.py` 现有纹理解析口径对齐。

### 3.3 与"完整性三档"的映射

| 完整性档 | 至少达到的 LOD 档 | 说明 |
|---|---|---|
| 外观壳 | LOD2 远景 + LOD1 观察 | 外壳只需远景/观察两档面数 |
| 内部蒙皮 | LOD1 观察 | 打开后可见内壁，用观察档面数 |
| 内部结构 | LOD0 特写 | 板卡/元器件/机构，用特写档面数 |

### 3.4 示例：apple-ii 整机的三档面数拆分（对 05 线 67 节点）

以 05 线 apple-ii（67 节点、`precision_level=L2`）为例，按 §3.1 档位拆解的面数预期：

| 装配体 | LOD2 远景 | LOD1 观察 | LOD0 特写 |
|---|---|---|---|
| case（整机外壳） | 200 | 2,000 | 12,000 |
| mainboard（主板） | 200 | 2,000 | 18,000 |
| keyboard（键盘） | 150 | 1,500 | 10,000 |
| power_supply（电源） | 80 | 800 | 6,000 |
| disk_ii（软驱） | 80 | 800 | 8,000 |
| 其余（子装配体合计） | 290 | 2,900 | 26,000 |
| **整机合计** | **≤ 2,000** | **≤ 20,000** | **≤ 200,000** |

> 说明：上表把 05 线 brief 里的"单模型 ≤20,000（L2）"解读为"观察档整机总量"，而非"单个装配体"，
> 以避免"整机 67 节点每个 ≤20,000 导致整机 134 万三角面"的误读（见 §9 衔接表口径对齐）。

### 3.5 面数测算与统计口径

- **"三角面"** 指 `mode == 4`（TRIANGLES）的 primitive 索引数 / 3；TRIANGLE_STRIP/FAN 按
  "顶点数 − 2" 折算（与 `budget_check.py` 现有 `count_triangles_exact` 一致）。
- **"单装配体"** = 一个 glTF 文件内所有 mesh 的面数之和；**"整机"** = 一个包内所有 `mesh_ref`
  的面数之和（当前 `budget_check.py` 只算单文件，聚合统计是 §8.1-1 的预研项）。
- **顶点数** 与面数分开统计（`POSITION` accessor count 之和），正式网格二者都要达标：顶点数
  过高但面数达标（如大量孤点、退化面）同样要优化。
- 预算数字是"上限"，不是"目标"；能用更低面数表达就不要顶格做，把余量留给明星件。

## 四、坐标系与单位

### 4.1 权威约定（与 Godot 一致）

- **单位**：一律**米**（SI），1 单位 = 1 米，模型按 **1:1 真实比例**建模。
- **坐标系**：**Y-up、右手系**（+X 右、+Y 上、+Z 朝向观察者），与 **Godot 4 一致**、与
  v0.2.1 §1.3 一致。
- **旋转**：单位四元数 `[x,y,z,w]`；glTF 内直接烘焙米制，运行时不得翻转。

> **勘误提示（针对任务文档）**：TASK-22B 任务文档中写"+Z 上，右手系，与 Godot 一致"存在
> **内部矛盾**——Godot 4 是 **+Y 上**（Y-up），"+Z 上"是 Blender 的默认。本草案以 **+Y 上**为
> 权威（与 Godot、v0.2.1、05 线 brief 三处一致），"+Z 上"视为任务文档笔误，列入 §10 开放问题，
> 由 v0.3 正式版统一裁决措辞。

### 4.2 建模工具坐标系（Blender 等 DCC 的 +Z 上）

多数 DCC（Blender、Maya、3ds Max）默认 **+Z 上**。生产时二选一：

1. **推荐：DCC 内保持 +Z 上建模，导出 glTF 时由导出器完成 +Z→+Y 转换**（glTF 规范本身就是
   Y-up；Blender 的 glTF 导出器会在导出时自动把 +Z 旋转到 +Y）。前提是**单位比例设对**（见 4.3）。
2. 备选：DCC 内直接设为 Y-up 场景（Maya 可选 Y-up），避免转换。

### 4.3 Blender ↔ Godot 导出对照表

| 项目 | Blender（源，+Z 上） | Godot 4（目标，+Y 上） | 转换说明 |
|---|---|---|---|
| 单位比例 | Scene → Unit Scale = **1.0**，Length = **Meters** | 导入后 1 单位 = 1 米 | **关键**：比例必须 1.0，否则导出后尺寸错 100 倍 |
| 上轴 | +Z 上 | +Y 上 | glTF 导出器自动 +Z→+Y（绕 X 轴 −90°），无需手转 |
| 前轴 | −Y 前 | −Z 前 | 导出器自动处理；避免在 DCC 内手改朝向 |
| 应用变换 | 导出前 **Apply All Transforms**（Ctrl+A） | — | 未应用缩放/旋转会烘焙进节点变换，导致 R-090/四元数校验异常 |
| 旋转 | 单位四元数 | 单位四元数 | 避免欧拉角万向锁；导出后核对模长=1 |
| 材质 | Principled BSDF | StandardMaterial3D / ORMMaterial3D | metallic/roughness 直接映射；见 §5 |
| 背面剔除 | 默认 | 默认 | 复古设备多为单面外壳，注意法线方向（见 §6.2） |

### 4.4 常见导出错误与规避

| 错误 | 后果 | 规避 |
|---|---|---|
| Blender 单位比例不是 1.0 | 设备尺寸放大/缩小 100 倍 | 导出前检查 Unit Scale=1.0 |
| 未 Apply Transforms | 节点带缩放/旋转，R-090 或四元数校验失败 | 导出前 Ctrl+A 应用全部变换 |
| 导出时未选 +Y Up | 设备在 Godot 里躺倒/颠倒 | glTF 导出器默认 +Y Up，勿手改 |
| 法线朝内 | 外壳正面被背面剔除，呈"镂空" | 导出后翻转法线或检查 winding |
| 内壁缺失 | 开盖后看到"纸片壳"背面 | 外壳给实体厚度，内壁单独建模 |

> 一句话：**Blender 里单位设米、比例设 1.0、导出前 Apply Transforms、导出 glTF 选 +Y Up**，
> 到 Godot 即可零误差落地。

## 五、材质与 PBR 贴图规则

### 5.1 PBR 管线与贴图类型

统一使用 **金属度-粗糙度（metallic-roughness）PBR** 管线，即 glTF 2.0 标准材质模型。每类贴图：

| 贴图 | 命名后缀 | 通道 | 说明 |
|---|---|---|---|
| 基础色 | `_basecolor` | RGBA | 反照率（albedo），**不得含光照信息** |
| 金属度-粗糙度 | `_metallic_roughness` | metallic=R，roughness=G | 合一张（glTF 标准 ORM 打包） |
| 法线 | `_normal` | RGB | 切线空间法线，+Y 向上 |
| 自发光 | `_emissive` | RGB | 复古设备的灯管/氖灯/指示灯用 |

**命名规则**：`<node_id>_<map>.png`，例如 `case_basecolor.png`、`crt_screen_emissive.png`。
**尺寸规则**：宽高为 2 的幂（512/1024/2048/4096），且 ≤ 该包 `precision_level` 对应纹理上限
（v0.2.1 §5），方图优先；正式交付前关闭不必要的 mipmap 链差异，统一生成 mipmap。

### 5.2 复古设备材质预设组（金属 / 塑料 / 玻璃）

| 预设 | metallic | roughness | 代表对象 | 备注 |
|---|---|---|---|---|
| 镀锌钢板/金属盒 | 0.9–1.0 | 0.35–0.5 | 电源屏蔽盒、机架 | 银灰，可用轻微锈蚀/拉丝噪声 |
| 米黄 ABS 塑料 | 0.0 | 0.7–0.9 | 机箱、键盘、软驱壳 | 哑光，年代感发黄 |
| 绿色 FR-4 PCB | 0.0 | 0.4–0.6 | 主板、电源板 | 深绿基色 + 金色焊盘/金手指 |
| 陶瓷 DIP 芯片 | 0.0 | 0.3–0.5 | 6502、ROM、TTL | 黑色/陶瓷灰 + 顶部丝印 |
| 玻璃 / CRT 屏面 | 0.0 | 0.0–0.1 | CRT 屏、指示灯罩 | 需透明/清漆（alpha mode BLEND）；自发光配合 |
| 纸盆喇叭 | 0.0 | 0.8–0.95 | 扬声器 | 粗纹理 |
| 真空管玻璃 | 0.0 | 0.05 | 电子管 | 透明 + 内部灯丝自发光 |

> 材质一律**自产或按实物参照人工重建**，不得直接贴版权照片（见 §5.3 红线）。基础色贴图里
> 的"年代感发黄"靠 roughness 噪声 + 低饱和 basecolor 实现，而非烘焙光照。

### 5.3 纹理来源红线（THIRD_PARTY 三件套延伸）

- 纹理来源分两档：**原创/自绘**（AI 生成 + 人工核对，标注"原创"）或**第三方**（CC0 或权利明确）。
- 第三方纹理必须沿用 v0.2.1 §8 的"三件套"：**许可分档（public_domain/cc/licensed）+ 来源 URL +
  获取日期**，写入该包的 `THIRD_PARTY.md`，并明确"该纹理用于 XXX 节点"。
- **禁止**：直接抠取实物照片、扫描说明书/包装图、使用版权字体做键帽丝印、使用商标/logo
  （如苹果彩虹标、品牌铭牌）作为贴图——商标元素只登记、不呈现（沿用 05 线 brief 的 FR-J2 约定）。
- 键帽字符、面板丝印必须**自绘**，避免字体版权风险。

### 5.4 贴图生产与压缩

- 正式网格贴图建议导出 **KTX2 / Basis Universal**（Godot 4 原生支持）用于运行时，源码保留 PNG；
  若仅存 PNG，Godot 导入时选择 VRAM 压缩（BC7/ETC2，视平台）。
- 法线贴图避免极端高频噪声（易在移动渲染产生摩尔纹）；emissive 仅用于真实发光件（灯管/氖灯/
  LED），不整面滥用。

## 六、glTF 版本约束

### 6.1 版本与格式

- 一律 **glTF 2.0**（`asset.version == "2.0"`），`.gltf`（JSON + 外置 .bin/纹理）或 `.glb`（单文件）。
- 网格数据：**三角形** primitive（`mode == 4`），索引化（`indices`），POSITION/NORMAL 必填，
  TEXCOORD_0 有纹理时必填。
- accessor 建议填写 `min`/`max`（包围盒），供引擎快速剔除与预算统计。
- 禁止：正式网格内嵌超大 base64 data URI（> 1 MB）；正式资产用外置 buffer/纹理文件。

### 6.2 法线与背面剔除

- 外壳等**单面**几何，法线朝外；打开后的**内壁**若可见，需单独建模内表面（不得靠双面渲染兜底）。
- 复古设备外壳多为薄壳，建模时给**实体厚度**（如 ABS 壳 2–3 mm），避免"纸片壳"穿帮。
- 三角形绕序（winding）决定法线方向，导出后若出现"镂空"，先查 winding 再查法线。

### 6.3 单位与变换烘焙

- glTF 内节点变换用米制；装配体的 `transform`（meta.json）是**装配级摆放**，网格顶点坐标是
  **局部几何**，二者不得重复表达同一偏移（否则拆解动画会错位）。
- 导出前 Apply All Transforms，保证节点局部变换为单位（translation=0、rotation=单位、scale=1），
  把实际几何写进顶点。

### 6.4 压缩与网格优化

- 复用几何用**实例化**（同 mesh 多 node 引用），不要重复导出相同的键帽/插座几何。
- 大网格可选 **Draco 压缩**（glTF KHR_draco_mesh_compression 扩展），但需确认 Godot 4 已启用
  对应导入插件；默认不启用 Draco，以兼容性优先。
- 顶点冗余（法线/UV 接缝）允许，不做强制 welded；但控制 accessor 数量避免过多 draw call。

### 6.5 复古设备建模常见坑

针对本项目这批早期计算机/个人计算机，建模时的高频易错点集中如下，提前规避：

| 易错点 | 表现 | 规避 |
|---|---|---|
| 直角方盒 | 机箱被做成无圆角方盒，与实物圆润造型不符 | 参照 05 线 brief 的"圆润无锐角"提示 |
| 芯片比例失准 | DIP 封装引脚间距/长度随意 | DIP 引脚 2.54mm 间距，按 datasheet 定 |
| 键盘键帽弧面缺失 | 键帽做成平面 | 键帽顶面给内凹弧面 |
| 面板丝印乱用字体 | 字符用版权字体 | 自绘字符纹理（§5.3） |
| 螺丝/接插件过度细化 | 每颗螺丝都做螺纹 | 螺丝用圆柱+十字槽即可，螺纹用法线贴图 |
| 线缆用面片 | 线缆成纸片 | 用细分圆柱或带状，给厚度 |
| 重复件逐个建模 | 52 键帽/8 槽逐个独立建模 | 实例化（同 mesh 多 node） |
| 内部走线全还原 | 电源盒内线缆全做 | 板级组合体合并，不做内部走线细节 |

### 5.5 材质预设组参考色值（sRGB 十六进制，供建模对照）

下表给出复古设备常见材质的 basecolor 参考起点（建模时以实物照片为准微调，非强制精确值）：

| 材质 | basecolor 参考（sRGB hex） | 说明 |
|---|---|---|
| 米黄 ABS 塑料（新） | `#E8E0D0` 一带 | Apple II 机箱年代感以 roughness 噪声 + 轻微偏黄呈现 |
| 米黄 ABS 塑料（发黄老化） | `#D6C9A8` 一带 | 长期氧化后的偏黄 |
| 绿色 FR-4 PCB | `#1F5A2E` 一带 | 深绿基色，金色焊盘用金属度贴图区分 |
| 镀锌钢板 | `#C0C4C8` 一带 | 银灰，metallic≈1.0 |
| 铝散热片 | `#B8BCC0` 一带 | 亮银，metallic≈1.0，roughness≈0.35 |
| 黑色 DIP 芯片 | `#1A1A1A` 一带 | 顶部白色丝印自绘 |
| 陶瓷芯片（灰） | `#C8C8C0` 一带 | 陶瓷灰，6502 用 |
| CRT 玻璃 | `#0E2A1A` 一带（暗绿）+ emissive | 关机态深色，开机态叠加 emissive |

> 金属/玻璃的"颜色"主要体现在 basecolor 的**低饱和灰阶**，真正质感由 metallic/roughness 通道
> 决定，建模时不要往 basecolor 里烘焙高光/阴影。

## 七、占位盒 → 正式模型替换协议

### 7.1 核心原则：同 node_id 即换，loader 零改动

1. 正式网格文件**同名替换**占位盒（`meshes/<assembly-id>.gltf` 或 `.glb`），节点名/网格名仍为
   `node_id`（R-090 不变），`meta.json` 的 `mesh_ref`、`assemblies[].id` **一律不动**。
2. 由此 loader 的定位逻辑（按 id 找节点）**零改动**，拆解/高亮/动画标注也无需重写。
3. 允许 `.gltf` 换成 `.glb`（反之亦然），但此时必须同步更新 `meta.json` 的 `mesh_ref` 扩展名——
   这是唯一允许的 meta 改动，且属"引用路径"而非"结构"变更。

### 7.2 增量交付约定（先外观壳、后内部结构）

- 阶段 1（外观壳）：先替换外壳/整机级网格，保证"可看"；
- 阶段 2（内部蒙皮）：开盖后可见的内壁/舱体；
- 阶段 3（内部结构）：板卡/元器件/机构/线缆，支撑"可拆/可懂"。
- 每一阶段**单独可合入**：替换后跑 `validate.py`（R-016 mesh_ref 存在、R-041 可解析、R-090
  命名）+ `budget_check.py`（面数预算），全绿即合入，不必等全部阶段完成。
- 尚未替换到内部结构的装配体，占位盒继续占位（占位盒必须保持 `node.name = node_id` 合法）。

### 7.3 替换自检清单

| 步骤 | 检查项 |
|---|---|
| 1 | 文件名 = `<assembly-id>.gltf`（或 .glb 且 mesh_ref 同步） |
| 2 | 场景根节点 `name` = `node_id`，根 `mesh` `name` 一致 |
| 3 | `asset.version == "2.0"`；米制、Y-up 右手系、法线朝外 |
| 4 | 面数 ≤ 该档 LOD 预算（§3）；纹理 ≤ 精度级上限（§5） |
| 5 | `python tools/validate/validate.py <pkg>` FAIL 0 |
| 6 | `python tools/validate/budget_check.py <gltf> --level L2` 预算内 |

## 十、建模生产流程与验收标准

本章把"从占位盒到正式模型"的完整流程与验收口径固定下来，供各内容线按图索骥。

### 10.1 生产流程（六步）

| 步骤 | 动作 | 产出 | 门禁 |
|---|---|---|---|
| 1 资料 | 核对 brief 条目表与证据包 [Sxx]，锁定尺寸/材质/易错点；"待实测"项未定值不开工 | 建模依据 | — |
| 2 整机 | 先锁整机比例与尺寸，再拆装配体 | 整机轮廓 | 尺寸定值 |
| 3 外壳 | 由整到零：外壳 → 主板 → 键盘/电源/软驱 → 元器件 | 外观壳 | 逐级 validate |
| 4 内部 | 开盖可见的内壁/舱体 | 内部蒙皮 | validate |
| 5 结构 | 板卡/元器件/机构/线缆 | 内部结构 | validate + budget |
| 6 合入 | 同名替换占位盒，跑全套校验 | 正式资产 | FAIL 0 + 预算内 |

### 10.2 验收口径（替换合入必须满足）

1. **结构**：`validate.py` 对该包输出 `FAIL 0`（R-016/R-041/R-090 全过）；
2. **预算**：`budget_check.py` 对该 glTF 按对应精度级输出"在预算内"（超限需评审豁免）；
3. **命名**：文件、根节点、根 mesh 三者与 `node_id` 一致；
4. **写实比对**：与实物/展项照片人工比对五项——1:1 尺寸、面数预算、命名、材质、商标元素；
5. **版权**：`THIRD_PARTY.md` 已登记纹理三件套，无版权素材、无商标贴图。

### 10.3 验收工具链现状与差距

- 现有：`validate.py`（R-016/R-041/R-090 结构 + 命名）、`budget_check.py`（单 glTF 面数/纹理）。
- 缺口：缺"整包聚合面数"与"材质引用完整性"（见 §8.1），正式开产前建议先补 S 档两项，
  M 档两项随第一批正式网格同步补。

### 10.4 预算豁免评审流程

当某个装配体因"明星件"或"真实复杂度"确实需要超过 §3 预算时，走以下豁免流程，而非直接放行：

1. **申报**：在内容包 README 或评审记录里写明"哪个节点、超多少、为何必须超"（例如 6502 CPU
   引脚丝印特写需要 1500 面，超观察档但属特写档内）；
2. **降档归口**：优先判断是否本就该用更高档（特写档），而非申请突破本档上限；
3. **全局对冲**：若确需突破，须在**其它装配体**上压缩等量面数，保证整机预算不超；
4. **评审留痕**：豁免与对冲结果记入该包完成报告，供 v0.3 正式版校准预算数字（预算本就可调）。

> 核心思想：预算是"整机总量约束"，不是"单装配体硬上限"；明星件可以高，但要有人为此"买单"，
> 避免每台都往高里做导致整机失控。

## 十一、示例：apple-ii 的 case 装配体完整建模对照

以 05 线 apple-ii 的 `case` 装配体（`mesh_ref = meshes/case.gltf`）为例，演示本章规则如何落地。

### 11.1 节点树（case.gltf 内部）

```
case.gltf
└─ scenes[0].nodes[0] = "case"          ← 根节点名 = node_id（R-090）
   ├─ mesh "case"                       ← 根 mesh 名 = node_id
   │   └─ primitive（外观壳：上盖+底壳+铭牌槽+提手+通风栅格）
   ├─ node "case_lid"   → mesh "case_lid"     （上盖，可独立掀起动画）
   ├─ node "case_bottom"→ mesh "case_bottom"  （底壳，可下沉动画）
   ├─ node "case_badge" → mesh "case_badge"   （铭牌，商标仅登记/皮肤替换）
   └─ node "case_vent"  → mesh "case_vent"    （通风栅格）
```

> 说明：case 是"内部蒙皮"级装配体（上盖可开，需见内壁），故拆出 lid/bottom/badge/vent 四个子节点；
> 若只是外观壳阶段，可先只交一个合并 mesh，后续再拆节点（拆节点需同步更新标注 target，成本高于
> 一开始就拆，故建模前先按"是否需单独寻址"定好节点树）。

### 11.2 三档 LOD 面数（case）

| 档位 | case 单装配体面数 | 说明 |
|---|---|---|
| LOD2 远景 | ≤ 200 | 整机远景只看到外壳轮廓 |
| LOD1 观察 | ≤ 2,000 | 默认交付，圆润曲面 + 散热槽可见 |
| LOD0 特写 | ≤ 12,000 | 拆解特写，开盖后内壁 + 卡扣结构可见 |

### 11.3 材质与贴图（case）

| 贴图 | 文件 | 尺寸 | 说明 |
|---|---|---|---|
| 基础色 | `case_basecolor.png` | 2048 | 米黄 ABS，低饱和 + 轻微发黄 |
| 金属-粗糙 | `case_metallic_roughness.png` | 2048 | metallic=0（塑料），roughness≈0.85 + 噪声 |
| 法线 | `case_normal.png` | 2048 | 轻微表面颗粒 + 散热槽凹槽 |

> case 的 roughness 噪声即"年代感发黄"的来源；铭牌（badge）贴图按 §5.3 只登记、皮肤替换，
> 不渲染商标（FR-J2）。

### 11.4 替换占位盒的完整动作

1. 用正式 `case.gltf` 覆盖 `meshes/case.gltf`（同名，节点名仍 `case`）；
2. `meta.json` 不改（`mesh_ref` 仍是 `meshes/case.gltf`，`case.id` 不变）；
3. 跑 `validate.py content/apple-ii` → FAIL 0；`budget_check.py meshes/case.gltf --level L2` → 预算内；
4. 合入。整机拆解动画（case 上盖沿 +Y 掀起）依赖的子节点名 `case_lid` 若在占位盒阶段不存在，
   需同步补上，否则拆解标注（如 `lid_role` 的 target）会因 R-015 悬空而 FAIL。

## 十二、对 loader 与引擎接口的影响（零改动承诺的边界）

本章替换协议承诺"loader 零改动"，其成立边界如下，超出边界才需改动引擎：

| 场景 | loader 是否需改 | 说明 |
|---|---|---|
| 同名替换 glTF（同扩展名） | 否 | 定位逻辑不变 |
| .gltf → .glb 切换 | 否 | loader 应已支持 .glb；仅 meta 同步 mesh_ref 扩展名 |
| 新增子节点（case_lid 等） | 否 | loader 按根节点定位，子节点不依赖 |
| 新增 mesh 引用（元器件独立成文件） | 需评估 | 若 loader 假设"一装配体一文件"，新增引用需确认装配逻辑 |
| 引入 Draco/KTX2 压缩 | 需评估 | 依赖 Godot 导入插件启用，属引擎配置而非内容契约 |

> 结论：在"同名替换 + 节点名不变"的约束内，正式建模对 loader/引擎**零改动**；一旦引入新扩展
> （压缩、新引用形态），改动的责任在引擎侧，内容线应提前与 01 线对齐。

## 十三、开放问题（留给 v0.3 正式版裁决）

1. **坐标轴措辞**：任务文档"+Z 上，右手系，与 Godot 一致"自相矛盾，本草案取 **+Y 上**；需 v0.3 正式版统一改口。
   *背景*：Godot 4 是 Y-up，Blender 是 Z-up，二者是导出转换关系而非同一约定，任务文档把两者
   混写会误导建模师，必须裁决一个权威措辞。
2. **LOD 编号约定**：本草案按 Godot 惯例 LOD0=最高模（特写）；任务文档"展台远景 LOD0 高模"措辞含混，需确认是否采用 LOD0=最高。
   *背景*：Godot 4 的 LOD 系统以 LOD0 为最高质量（最近），索引越大越远；若项目采用相反编号
   （LOD0=最远），会与引擎语义冲突，必须定死。
3. **"单模型"口径**：预算表的"单模型三角面"到底是单装配体、单 glTF 还是整机，需正式版定义清楚（§8.1-4）。
   *背景*：v0.2.1 §5 的"单模型"列与 05 线 brief 的"单模型≤20000"口径不一致（前者易读作整机，
   后者读作装配体），本草案 §3.4 已给出对齐解读，待正式版确认。
4. **三档 LOD 的文件组织**：是"同名文件分阶段替换"（§2.3 当前约定）还是"`_lod0/_lod1/_lod2` 三文件并存"，需正式版定。前者省事、loader 零改动；后者支持运行时距离 LOD 切换但需 loader 支持。
   *权衡*：单文件分阶段替换契合"增量交付 + loader 零改动"的当前诉求；多文件并存契合远期
   运行时 LOD 性能诉求。短期建议前者，远期可平滑升级为后者（多文件时命名约定见 §2.5）。
5. **纹理是否纳入 R-0xx 阻塞**：v0.2.1 纹理超限不阻塞（budget_check 报告）；正式网格是否把纹理尺寸/面数升级为可阻塞的 validate 规则，需评审。
   *背景*：正式开产后纹理尺寸/面数失控是常见返工源，建议对"面数"至少做到 warn 级别、对
   "纹理尺寸超精度级上限"做到 fail 级别，具体口径待评审。
6. **装配级 LOD 与 precision_level 的权威关系**：若三档 LOD 落地，`meta.precision_level` 是否仍为唯一权威档位声明，或新增 `meta.lod_levels` 字段，待定。
   *背景*：新增字段会触发 schema 变更（additionalProperties 放行），影响面较大，倾向"沿用
   precision_level 为权威，三档 LOD 只作生产指引"的轻量方案。
7. **透明/折射材质**：CRT 玻璃、真空管的清漆与透明，Godot 移动渲染器的 alpha 排序开销，需实测确定是否统一用 BLEND 还是 OPAQUE+emissive 假透明。
   *背景*：移动渲染器透明排序性能差，CRT 屏面这类"黑底亮斑"用 OPAQUE + emissive 即可假透明，
   无需真透明；真空管才可能需真透明，需实测。
